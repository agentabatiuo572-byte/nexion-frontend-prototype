# 试用提前转购优惠详细方案与实施交接

状态：2026-10-28 产品确认三项决定，前后台实现已合入/推送（FEAT-TRIAL05），**待 TEST 部署后验收**，接手请直接看文末[实施结果与待验收](#实施结果与待验收2026-10-28)。生效以后端迁移随版本部署为准，部署前三端收不到 `quote` 字段即沿原累计规则展示与结算。已确认：①固定立减首发 10 USDT，迁移直接种子为 10，后台可改 0–100（0=整套关闭）；②未结束的旧领取单只要转购时服务端确认仍在原试用期内、领取快照完整即适用，快照缺失沿旧规则；③退款全额退回实付，按新政策发放的 USDT/UVT 奖励经现有 `recoverReward` 仅追回可证明未花用部分，不产生负余额、不扣其他收益，未追回余额写审计 `H2_TRIAL_REFUND_REWARD_MANUAL_REVIEW` 转人工复核；旧规则订单退款行为不变。下文保留评审版原文作为规则依据，与上述决定冲突处以上述决定为准。按交付要求仓库不包含可点HTML原型。

现行行为：只提供“提前购买”入口，并未消除等待获得更多试用权益的优势。`AppTrialLifecycleService.settlement` 按已过时间算 USDT/UVT；`remainderUsdt` 是已累计 USDT 超过抵扣上限的部分，不是剩余天数的收益。购买即关闭试用；通用转购促销早买晚买相同。

最新用户目标：现在购买须比试用到期后购买更划算、拿到更多购机利益，同时控制前后台改动量。

推荐：**完整试用权益照拿，试用中购买再享固定立减**，示例额外减10 USDT，实际由后台配置。真实已累计仍按真实时间显示；尚未累计的部分单列“提前转购奖励”。不将未来预计产出伪装成已赚收益，也不提高正式设备收益率或承诺更高实际收益。仅补至领取时固定原试用期的总权益；额外立减只在服务端确认试用仍有效时适用，宽限/延期不享额外早购优惠。

相较“买后继续到原到期日逐笔归集”，一次转购补齐更容易向用户说明，并可复用现有原子订单与奖励账务；代价是提前发放奖励的成本和退款逆向必须正式支持。这是新政策，必须确认后才能实现。

#### [FEAT-TRIAL05] 提前转购完整权益

**① 用户故事**

作为正在试用、已经决定购机的用户，我想提前购买时保留完整试用购机权益并多享一笔购机优惠，以便现在买比到期后买更划算。作为运营人员，我想用一个固定优惠参数控制实际累计、提前转购奖励和额外优惠成本，以便审核预算、退款和异常领取。

**② 验收(GWT)+异常路径**

- Given 支持本政策的有效领取单、商品可购且付款条件满足 When 用户确认提前转购 Then 服务端按领取快照原天数计算完整 USDT/UVT 权益，把未累计差额记为转购奖励；同一事务完成扣款、抵扣、余款/UVT奖励、订单、正式设备及关闭试用。正式设备按实际支付成功时间激活，试用不再二次产出。
- Given 同一领取单、同一商品价格和通用优惠且应付足够抵减 When 比较试用中买与到期后买 Then 完整试用抵扣、超额USDT奖励和UVT总额一致，提前购买额外少付已配置的固定立减，设备更早激活。不得声称正式设备的未来实际收益一定更高。
- Given 固定早购优惠10 USDT且原应付款大于10 When 服务端确认仍处ACTIVE Then 实付再减10；到期后GRACE/EXTENDED保留原优惠但不加10。若原应付款小于10，仅减至0，明确显示本单实际额外优惠，禁止宣传全额10或产生负价格。到期/政策版本变化使金额增加时须重新确认，不在提交阶段静默多扣。
- 异常1：Given 旧领取单没有完整有效快照、活动未启用、或新政策报价失败 When 进入结算 Then 不展示补齐承诺，明确沿原规则报价或提供重试；不能把缺失值补零，也不能在支付确认后静默切换规则。
- 异常2：Given 库存不足、容量冲突、余额不足、奖励准备金不足 When 提交 Then 整笔不成功，试用保持原状态且不消费奖励资格；余额仍按现行规则校验应付款，待发奖励不提前当成可用余额。
- 异常3：Given 支付结果未知或重复点击/跨端重试 When 重新查询 Then 用同一订单/领取单/幂等键恢复，扣款、奖励、设备仅发生一次。报价版本或应付款增加需要重新确认；不同报价政策不可混用同一意图。
- 异常4：Given 购买取消/支付失败 Then 不授予提前奖励。Given 已付订单按现有制度获准退款 Then 必须按原订单快照一并逆向处理实付、抵扣、超额USDT及UVT奖励；未花用部分原路冲回，无法完整冲回时进入现有人工处置流程，不自动制造负余额、不扣其他设备收益、不暗改退款资格。退款规则/账务未接通前不得启用活动。
- 异常5：Given 已转购、取消或已失效领取单 Then 不补发、不追溯赠送、不重开试用。GRACE/EXTENDED仍按原完整天数封顶。已有未结束领取单可在后台发布明确的兼容政策后采用，服务端返回新政策版本；历史已完成交易不改账。

**③ 数据字典+生成规则**

下列新增字段为建议契约名，尚不存在；均由服务端生成并绑定领取单、报价与订单，客户端只展示。现行参数仍以领取快照和既有促销权威源为准，不增加客户端计算权。

| 字段 | 类型 | 规则 |
|---|---|---|
| settlementPolicy/version | string/number | 活动发布版本，建议新值 FULL_TERM_ON_CONVERSION；默认未启用 |
| earlyPurchaseDiscountUSD | decimal | 唯一新增运营金额参数，复用现有H2政策表与编辑接口；0表示不启用新早购方案。示例10，须非负且通过既有金额/预算校验 |
| accruedUsdt/accruedUvt | decimal | 真实已过时间×领取日额度，原天数封顶；保留原累计事实 |
| fullTermUsdt/fullTermUvt | decimal | 领取日额度×领取原durationDays；不含宽限/延期，不受后来活动改值影响 |
| earlyRewardUsdt/earlyRewardUvt | decimal | max(完整期权益−真实累计,0)，明示为提前转购奖励 |
| earlyDiscountAppliedUsdt | decimal | ACTIVE且新政策启用时，min(配置固定立减,原应付)，其余为0；原discountRate/discountCapUSD通用促销保持不变 |
| offsetUsdt/remainderUsdt | decimal | 按现行抵扣上限/余款公式处理完整期USDT，通用优惠与实付封顶保持原契约；价格过低等无法有效适用的报价拒绝并说明 |
| amountUsdt / quoteVersion | decimal/string | 服务端最终实付及确认版本；与既有通用优惠一起报价，不新增叠券能力 |
| settlement entries | ledger refs | 对领取单/订单/币种/奖励类型建立唯一性，退款引用同一组原流水 |
| settled_trial_nex | nullable decimal | 建议在现有领取单增加一个结算UVT总额列；真实shadow_accrued_nex不覆盖。历史NULL按旧累计值回落，客服资金核对SQL仍输出原形状的总发放金额 |

示例仅用于解释，**不是当前商品报价**：价格$1,299，原试用3天，日USDT额度$38.52、日UVT额度10，抵扣上限$50，忽略双方相同的通用优惠。试用12小时已累计$19.26和5 UVT；完整期为$115.56和30 UVT。

| 时点/规则 | 购机抵扣 | 应付 | 购后超额USDT奖励 | 购后UVT |
|---|---:|---:|---:|---:|
| 现规则，12小时买 | $19.26 | $1,279.74 | $0.00 | 5 |
| 等满3天买 | $50.00 | $1,249.00 | $65.56 | 30 |
| 推荐规则，12小时买，另享$10早购立减 | $50.00 | $1,239.00 | $65.56 | 30 |

推荐规则需额外列示补足$96.30和25 UVT，再列$10提前购买优惠；其中USDT补足与已累计合并后才按抵扣上限分配，不能只补$50抵扣却漏掉$65.56余款和UVT。相较“等满期再买”，完整试用总权益相同、平台多承担$10早购优惠；相较“原本就会早买”，还多承担未累计权益的补足。用户明确多省$10，而非被承诺设备日收益增加。

**④ 状态机+禁止动作**

领取单现行状态机不变。报价：读取中→有效报价→二次确认→提交中→已转购；网络不明→查单→原成功或可重试。奖励记录与订单同事务成功，退款逆向沿既有退款流程并记录对应奖励处置。禁止支付前发奖励、实际累计被补足额覆盖、重复发放、转换后继续积累试用、客户端承诺服务端未发布政策、已退款重用领取资格。

**⑤ 交互说明与四态**

默认：紧凑设备行仍只展示机型、小图试用角标、状态和剩余时间；展开/详情展示真实已累计，主文案“完整试用权益照拿，现在购买再减$10”（数值以本单实际报价为准），旁列试用抵扣、早购立减、购后USDT奖励和UVT。主按钮展示最终应付；到期后隐藏早购优惠并保留原本权益。说明正式设备从支付成功后开始运行，实际任务收益按既有规则。

空状态：没有支持新政策的领取单时不显示完整期补齐利益，不凭演示配置生成报价；回到可领取介绍或当前真实政策详情。加载态：金额位置保留骨架、提交禁用，避免旧报价短暂当新报价。报错态：报价读取失败可重试；库存/余额/准备金不足给出原因及返回出口。极限态：320宽、长语种、长金额、宽限期统一处理，权益三项可换行，不拥挤在默认队列行。

文字交互顺序：用户展开试用行或进入试用详情→查看真实累计、补足奖励及本单早购立减→进入结算读取服务端报价→确认金额与权益→支付成功后展示订单、奖励到账结果和已激活设备。取消则回到上一层；报价失败保留返回和重试；结果未知先查原订单。详情与结算的金额必须来自同一政策版本，不能把本文示例写死为实际报价。

**⑦ 跨文档一致性**

本提案获准前不覆盖主PRD §5.4/§5.6/§9.11/§12.18及 FEAT-TRIAL03/04 的现行金额合同。实施时需同步后端活动可配置政策、state/quote/convert响应与奖励退款账务、APP详情/结算/规则三语，以及主会话最终H5同步。现行 `remainderUsdt` 仍表示超额已累计USDT，不借用它表达尚未发生权益。正式实现必须补齐早晚同权益、全部币种、报价变化、退款、旧单、准备金不足与幂等测试后方可上线。

工程控制：复用现有转购事务、奖励流水、幂等键、订单和设备激活；不新建收益账户/奖励表，不加每日补发任务、优惠券或阶梯优惠。建议工程面为：H2键值政策表新增一个金额参数及管理白名单/元数据；现有领取表增加一个可空结算UVT列及资金核对SQL兼容投影；转购服务和报价增加完整期补足/固定立减；前端详情、结算、规则说明三语展示及针对性测试。退款和资金核对复用原链，但必须接入本次奖励快照，不能省掉这一步来声称只改几个显示字段。

### 建议实施顺序

1. **固定契约和样例。** 明确上述政策决定，使用本文早买/晚买对照数据冻结API预期值；保留旧政策样例，确认通用促销不变。
2. **先做配置与兼容迁移。** 新参数默认0；旧领取单NULL结算值继续按旧值读取。同步重领清空、管理参数白名单和资金核对投影，先验证旧行为不变。
3. **实现服务端报价。** 基于领取快照原天数计算完整期权益及补足额，再沿现有抵扣/通用促销规则计算基准应付，最后应用有界早购立减。金额舍入遵循既有资金精度，不使用前端浮点结果作为结算输入。有效提前购买还须校验服务端时间未到原试用截止点，不能只看尚未被定时任务推进的ACTIVE枚举。
4. **实现同事务转购。** 用已有领取单/账号锁和幂等边界复算报价，完成扣款、抵扣、双币奖励、订单、设备及试用关闭。任一步失败不消耗资格、不发部分奖励；重复命令回到原结果，结果未知先查单。
5. **接通退款与资金核对。** 由原订单快照找到实付和所有奖励流水，按原退款制度冲正；无法完整追回时进入已确认的处置流程。此步骤未通过时保持新政策关闭。
6. **接入APP并同步H5。** API解析、状态层、详情、结算、规则说明三语依次接入；空/加载/失败/报价变化保留返回、取消与重试。按现有APP/H5同步流程交付共享显示内容，不改变原生功能边界。
7. **定向验收后启用。** 先验证参数0仍走旧规则，再验证新规则；后端、前端及账务核对就绪后由运营启用配置。关闭参数只影响新报价，不追回已支付订单已获得的权益。

### 实现要点

- **报价唯一来源**：`AppTrialLifecycleService.quote()`。`GET /api/trial/state` 对进行中的领取单返回 `quote`（`settlementPolicy`、`quoteVersion`、`earlyPurchase`、`accruedUsdt/Nex`、`settledUsdt`、`rewardNex`、`earlyRewardUsdt/Nex`、`offsetUsdt`、`remainderUsdt`、`promoDiscountUsdt`、`earlyDiscountConfiguredUsdt`、`earlyDiscountUsdt`、`discountUsdt`、`amountUsdt`、`earlyEndsAtEpochMs`）；`convert()` 用同一函数复算。顶层 `shadowUsdt/offsetUsdt/remainderUsdt` 仍是真实累计口径，旧客户端不受影响。
- **适用判定**：参数 > 0、领取快照完整（天数、日 USDT/UVT、抵扣上限、价格、起止时间）、库内状态 CLAIMED/ACTIVE 且服务端时间早于 `expires_at`。GRACE/EXTENDED、快照不全一律走 `ACCRUED_ON_CONVERSION`。
- **确认版本**：`POST /api/trial/convert` 可带 `quoteVersion`。早购版本在整个原期内恒定，与服务端当前版本不同返回 409 `TRIAL_QUOTE_CHANGED`；原有“应付上涨”校验 `TRIAL_AMOUNT_MISMATCH` 保留。客户端两者都按“报价已变化”处理并重新读取 state，要求用户重新确认。
- **结算落库**：同一转购事务，奖励沿用 `H2_TRIAL_REMAINDER`（USDT）/`H2_TRIAL_BONUS`（UVT）入账。`shadow_accrued_*` 存真实累计，`remainder_usdt` 存实发 USDT 余款，`settled_trial_nex` 存实发 UVT；`settlement_snapshot` 追加 `settlementPolicy=…,quoteVersion=…,earlyRewardUsdt=…,earlyRewardNex=…,earlyDiscountUsdt=…`。资金核对投影改为 `COALESCE(settled_trial_nex, shadow_accrued_nex)`。`trial.redeemed` 事件载荷不变。
- **退款冲正**：`E4OrderRefundSettlementFacadeAdapter` 照常全额退实付，再调用 `TrialConversionRewardReversal`。仅快照含 `settlementPolicy=FULL_TERM_ON_CONVERSION` 的订单：退款事务内写审计 `H2_TRIAL_REFUND_REWARD_PENDING`；退款提交后 USDT、UVT 各在独立新事务经 `EarningsReleaseService.recoverReward` 追回可证明未花用部分（记 `nx_earnings_source_recovery`，追回额另记 `nx_wallet_ledger` `TRIAL_BONUS_REVERSAL`/OUT），最后写 `H2_TRIAL_REFUND_REWARD_REVERSED`，有未追回余额或追回异常则写 `H2_TRIAL_REFUND_REWARD_MANUAL_REVIEW`（`detail_json.rewards` 含 issued/recovered/outstanding/error）。追回失败不会让退款失败；只有 PENDING 没有终态即追回中断。
- **前端**：`src/api/trial-api.ts`（`parseTrialConversionQuote`、回执 `settlement`）、`src/store/free-trial.ts`（`authoritativeQuote`，转购意图含报价版本，旧三元意图原样重放）、`src/pages/me/trial.vue`、`src/pages/store/checkout.vue`、文案 `src/i18n/trial-lifecycle.ts`（H5 Lite 为 `src/i18n/trial-early-purchase.ts`）。原期结束时页面判定报价过期并重新读取，不展示也不支付过期优惠。预览桩 `scripts/lib/prototype-demo-trial.mjs` 镜像了服务端报价，`npm run preview:prototype` 后把 `trialState` 设为 `active` 即可看新界面。
