# 客服会话连续性与用户侧清空

日期：2026-10-27。来源：本轮消息列表批注及随后“客服后台保留完整记录”的补充要求。

## 会话与未读

- 同一账号与同一客服只显示一个会话入口，继承该客服的历史消息。以服务端稳定客服 ID 识别；不得用显示名称合并，不同客服不能串历史。
- 旧会话编号可以保留为服务端记录单元；前端显示为同一会话。重新进入、发送、重新登录后继续已有记录，不因打开页面额外创建空会话。
- 列表右侧显示未读数字；完整的本地化日期时间放在消息摘要下方，窄屏允许自然换行。数值属于该客服会话，不同客服之间不混算。未知仍为未知，不能伪造零。
- 进入会话后按实际读取的服务端消息边界确认已读，不能仅在列表点击时清零。历史分页、发送失败重试及消息幂等规则继续生效。

## 删除入口与确认

- 删除列表底部的“管理会话”。会话行左滑露出红色删除操作；滑动本身不删除，也不打开会话。
- 同时只展开一行，纵向滚动不触发左滑。反向滑动或点击已展开的内容区收起。为键盘提供左右键、Escape 和 Delete 等效操作。
- 点击删除后确认：

  **删除会话？**

  将清空你与该客服的全部聊天记录，重新登录或换设备后也不再显示。客服端仍保留完整记录；后续新消息正常接收。

  操作：取消 / 删除并清空。

- 取消不改变数据；确认等待服务端成功，失败保留列表及记录并允许重试。沿用全局确认弹层与 Home Indicator 安全距离。

## 清空范围——用户 2026-10-27 明确补充

这是**用户侧历史可见性清空**，不是物理删除客服记录，也不是只清本机缓存。

- 服务端按账号与客服保存清空边界。用户本机、其他设备、重新登录后的列表、历史分页与消息详情都必须服从该边界。
- 客服后台保留完整历史；用户清空不能删除客服端消息、附件或审计记录。
- 旧消息不再对用户显示；边界后的新消息可重新显示同一客服会话，并继续累积未读。
- 用户侧缓存、草稿和已清空消息相关发送状态随成功响应清理；发送及后台历史仍服从既有幂等和权限规则。
- 清空应覆盖该客服的所有旧会话编号。旧分页响应不得把已清空历史带回用户视图。

## 接口与验收边界

当前正式后端已有的 dismiss 只隐藏列表，不能兑现跨登录、跨设备清空。前端与原型必须使用独立的用户侧清空能力契约，不能将 dismiss 改名后当作清空成功。

本轮原型提供可验证的服务端模拟；正式能力开关未就绪时不显示可执行的删除操作。真实后端实现、部署与双设备联调列入审查报告的后置项，不得以原型通过冒充上线。

### 本轮前端能力契约

| 接口 | 契约 |
| --- | --- |
| `GET /api/app/support/conversation-management` | `{ clearUserHistory, clearedPeers }`。清空边界从服务端账号恢复，不依赖设备缓存。404 视为能力未上线；鉴权或服务故障正常报错。 |
| `DELETE /api/app/support/conversations/{cid}` | 幂等请求头；正文 `{ scope: 'USER_VIEW', peerKey, conversationIds, expectedVersions }`，覆盖该客服全部旧会话编号并核对版本。 |
| 成功结果 | `{ scope: 'USER_VIEW', userScopeCleared: true, peerKey, throughMessageId, conversationNos }`。只推进用户可见边界，不能物理删除后台消息。 |
| 原命令读回 | 结果类型 `CONVERSATION_USER_CLEAR`，结果体同上；重试复用原幂等键，不把超时当成功。 |

`peerKey` 使用稳定客服 ID，缺失时以原会话编号隔离。`throughMessageId` 为服务端有序消息边界。会话列表、旧 CID 详情、历史分页、实时消息恢复、发送命令读回均需应用边界；后台管理端查询保留原记录。前端清理成功范围内的缓存及旧草稿，后续新消息和新草稿不被旧清空回执覆盖。

正式服务还需按账号与客服原子复用会话，避免多个客户端同时首建产生新的重复记录。原型已有同客服复用及旧编号归组；前端不会用相同显示名称猜测两位客服是同一人。
