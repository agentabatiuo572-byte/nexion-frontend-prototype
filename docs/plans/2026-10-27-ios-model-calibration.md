# Android / iOS 手机算力规则修订与 iPhone 机型区间校准方案

日期：2026-10-27。状态：**仅方案，尚未实施**。本次交付只包含文档和预设数据草案；不修改功能代码、不执行数据迁移、不发布后台配置、不宣称真机验证完成。

## 1. 已确认的产品要求

1. Android 与 iOS 原生 App 都是手机算力目标平台，取消“手机算力仅支持 Android”“iOS 不执行手机任务”的产品限制。
2. iOS 校准只需可靠识别机型，按后台机型规则分配算力；不以 SoC、GPU、内存字段缺失拒绝 iOS 校准。
3. 用户已确认：**按机型匹配，不区分容量；算力范围标为运营预设值。** 例如 iPhone 16 Pro 的 128GB、256GB、512GB 等容量共用一个机型规则。
   用户随后明确目录范围：**从 iPhone 6 起，覆盖全部已发布并销售过的 iPhone**，包括各代 SE、Plus、mini、Pro、Pro Max、Air 等系列；不能只覆盖目前在售机型。
4. 后台预置机型及算力上下限，运营者可查询、新增、修改、停用和删除；发布沿用既有 E6 权限、A2 审批及版本记录。
5. App 识别机型后，校准结果在该机型有效区间内产生，服务端保存，前端读取并展示。
6. H5 保持原生执行边界：可查看手机状态及引导打开 App，不执行手机硬件采集、校准、激活、手机心跳或任务。

下文的抽取精度、结果复用、发布及历史兼容属于本方案的实施建议，不冒充额外的用户确认。

## 4. 后台数据结构与兼容

建议在现有版本化手机策略内增加 `iosModelRules`，与既有 Android 硬件规则 `rules` 分开，避免放松 Android 校验。继续复用现有 JSON 配置存储、revision、定时生效、A2 发布和大小限制，不为本需求另建通用规则引擎。

每个 iOS 机型规则包含：

| 字段 | 用途 / 约束 |
| --- | --- |
| `id` | 稳定、唯一的规则编号；编辑不换编号。 |
| `model` | 规范机型名，例如 `iPhone 16 Pro`；平台固定为 iOS。 |
| `aliases` | 原生 SDK 可能返回的已核验名称别名；可编辑，不能跨机型重复。 |
| `minComputeValue`、`maxComputeValue` | 正数，建议最多 2 位小数，`0 < min <= max <= 1000000`；相等时为固定值。 |
| `enabled` | 是否参加后续校准匹配；停用不会删除历史结果。 |
| `valueSource` | 固定为 `OPERATOR_PRESET`，用于正确展示数值性质。 |
| `catalogClass` | 官方在售快照 / 历史已售；不参与算力计算，也不排除历史机型。 |
| `note` | 运营说明、机型识别依据；禁止当作性能实测证明。 |

规则版本和生效时间沿用外层策略，不在单条规则重复维护。容量、颜色、地区 SKU 不参加匹配。初期最多 500 条 iOS 机型规则，并继续检查整份配置的实际字节限制。

兼容原则：

- 旧 JSON 缺少 `iosModelRules` 时按空集合读取；旧 Android `rules`、固定算力、档位和结果不重写。
- 已有 iOS 硬件规则不静默自动转换成机型区间。运营先核对再停用或迁移，新的 iOS 匹配只采用已发布的机型规则，避免两种规则争抢同一请求。
- 删除规则只影响新校准；历史校准保存的规则编号、版本、上下限和值仍可回溯。
- 预设导入只补齐缺少的机型，不覆盖已编辑区间、别名和停用状态；显示本次新增、跳过和冲突项。
- 服务端统一校验唯一机型 / 别名、范围、精度和配置大小；后台校验用于及时反馈，不能替代服务端边界校验。

## 5. App 机型识别与校准交互

1. iOS 原生 App 通过原生系统信息接口读取 `deviceModel`，必要时使用同一原生接口的 `model` 字段；不能使用用户可编辑的设备昵称或浏览器 UA 作为机型。
2. 提交 `platform=ios`、原始机型、现有安装标识及校准请求；iOS 不要求 SoC、GPU、RAM、容量字段。Android 继续使用现有硬件采集规则。
3. 服务端执行规范化与精确别名匹配：处理大小写、Unicode 和受控空白差异；禁止用“包含 Pro”等模糊关键词猜型号，也不能把 `iPhone` 通称匹配成某个具体型号。
4. 同一别名指向多条启用规则时发布失败；未知机型进入待核验，提示重试或联系客服，允许用户继续普通账户业务，不授予算力。
5. 机型命中后，校准页面显示机型、运营预设范围和状态。例如“iPhone 16 Pro · 运营预设范围 100–120”；成功后显示服务端保存的结果，如 `113.42`。
6. 激活确认沿用现有校准结果、安装绑定、槽位和换机资格检查；GET 回读确认后才显示已激活。
7. 进度文字使用“正在识别机型 / 正在匹配算力规则”，不显示实际没有执行的“GPU 压测”“真实 TOPS 测试”或伪造跑分动画。
8. 设备仓库、赚取页、校准引导、登录恢复、首次设置、课程提示和三语文案统一清理 Android 独占描述。原生能力暂不可用是可恢复状态，不能显示平台永久不支持。
9. H5 不展示可提交的校准、激活或手机执行按钮；保留手机状态和打开 App 的正常引导。不能通过注入 iOS / Android bridge 绕过 H5 编译门。

机型读取依据：[uni-app 系统信息接口](https://uniapp.dcloud.io/api/system/info?id=getsysteminfo)。SDK 不能识别的新机先待核验，更新 SDK 或经核验的名称映射后再开放，不根据目录预设冒充识别成功。

## 6. 区间分配、持久化和防止反复抽取

建议的默认行为是：**一次成功校准分配一个值；重复请求、刷新、重新登录和同机恢复读取同一结果。** 用户看到区间内的稳定值，不在每次渲染时变化。

- 服务端在首次成功保存该账号、安装、规范机型与规则版本的校准结果时，以服务器随机源在闭区间内分配一个两位小数值。
- 客户端不提交最终算力值，也不自行抽取；篡改机型以外的 `computeValue` 等字段不能覆盖服务端结果。
- 既有幂等键、revision、安装绑定和事务继续生效。相同幂等请求回放原响应；同一安装同一版本显式重试也复用已保存的校准结果，不因换一个幂等键重新抽取。
- 保存：原始 / 规范机型、规则编号 / 版本、上下限、最终值、数值来源、校准时间和安装绑定。原始容量不需要采集或保存。
- `PhoneCalibrationPolicy.match` 保持纯匹配：返回命中的规则和区间；试算、影响预览、GET 与激活复核不得抽取随机值。
- `OnboardingCalibrationService` 首次成功校准时负责分配和落库。后续激活复核改为检查保存值是否位于保存规则区间、版本是否有效、档位是否一致，不能重新随机后比较两个值。
- 规则发布后不重抽已激活设备、不改历史结算。未激活的过期结果按现有规则变更流程提示重新校准；新版本的分配也需保存并复用。
- 同机重装、换机、安装标识丢失仍走现有账号绑定和换机策略，不能仅删除本地数据就绕过业务绑定重新抽取。

正常示例：首次校准 iPhone 16 Pro → 命中 100–120 → 保存 113.42 → 激活回读 113.42 → 刷新、登录恢复仍为 113.42。管理员试算只显示“机型命中，范围 100–120”，不产生用户分配记录。

## 7. E6 后台页面与增删改查

在现有“手机硬件算力规则”区域增加“iPhone 机型预设”子区域，保留 Android 硬件规则及共用档位入口。

**列表**：机型、别名、运营预设下限 / 上限、启用状态、目录分类、当前版本。支持机型搜索、启用状态 / 目录分类筛选、清空筛选和无结果提示。

**新增 / 编辑**：使用独立字段输入机型、别名、上下限、启用状态和说明；不要求填写 SoC、GPU、内存或容量。显示与其他机型的名称 / 别名冲突；输入非法时保留草稿并定位字段。

**预设导入**：按钮“载入 iPhone 机型预设”读取版本化预设目录，展示从 iPhone 6 起的全部 47 个已售机型，默认全选；运营者可筛选或取消部分选择，但不能把历史机型隐藏成未支持范围。未填写档位时导入不猜测既有收益配置。未保存的导入只是草稿，不代表生效。

**删除 / 停用**：草稿新增项可直接移除；已发布条目删除或停用进入发布差异。确认提示明确“影响后续校准，已分配算力及历史记录保留”，不清空用户记录。

**试算**：选择 iOS 后只需要机型；结果显示命中规则、区间、可能覆盖的档位及数值性质。Android 保留现有 SoC/GPU/内存表单。区间跨档时展示可能档位，最终档位按保存的分配值计算，不用区间中点冒充最终结果。

**发布**：复用 E6 编辑权限、A2 提案、不同管理员审批、生效时间和版本冲突处理。A2 展示新增 / 修改 / 删除、机型区间前后值、停用项及历史结算不变；不能继续只显示一个固定 `computeValue`。审批失败、过期、并发变更或回读失败均保留可恢复反馈。

## 8. API 和预设初始化实施建议

复用 `/api/admin/config/phone-calibration` 的查询与 `/preview`，以及既有 A2 写入路径；不另建一套绕过 A2 的直接发布接口。

- 查询结果的当前 / 待生效策略增加 `iosModelRules`；旧客户端不能丢弃这个字段后整份覆盖保存，需同轮更新后台客户端校验与 A2 提案解析。
- 新增只读预设目录接口建议为 `GET /api/admin/config/phone-calibration/ios-model-presets`，沿用 E6 读取权限；返回目录版本、核对日期、来源链接和预设规则。
- 预设目录建议作为后端版本化资源发布。载入预设只填后台草稿，按差异审阅和 A2 发布后才写入正式配置。
- App 校准结果在现有字段之外建议返回 `calibrationMethod=IOS_MODEL_RANGE`、规范机型、范围和 `valueSource=OPERATOR_PRESET`；保存值仍复用现有 `computeValue`、`tier`、`ruleId`、`ruleVersion`。
- `computeUnit` 保持 `platform`。跨平台字段缺失按校准方法判断，不能把 iOS 缺少 SoC 当成硬件异常，也不能因此放宽 Android。
- 需核对当前校准行和结果 JSON 的容量、序列化及回读：优先复用已有结果快照；只有发现字段存储确实不足时才增加必要迁移。

本次不会运行上述接口、初始化生产数据或提交 A2 提案；JSON 草案不等于后台已配置。

| S4 App / H5 | iOS 原生机型读取、平台门、校准结果呈现、三语清理、H5 只读 | Android/iOS 原生编译通过；H5 注入 bridge 仍不能提交手机操作；页面无 Android 独占提示。 |
| S5 联调交付 | 正式 App、后端、后台、H5 对齐、PRD 与交接记录 | 本机针对性回归、相关构建、真实 UI 操作和接口回读完成；Android/iPhone 真机证据单列，未执行项不标通过。 |

实施顺序先后端合同和持久化，再后台、App，最后同轮同步 H5。正式发布前核对数值与档位、收益规则的关系；不因为本轮预设范围较高就默认修改收益、阈值或设备历史数据。
