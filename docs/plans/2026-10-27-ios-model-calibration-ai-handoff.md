## 二、用户已经明确的产品要求

1. Android 和 iOS 原生 App 都支持手机算力业务，取消“手机算力仅支持 Android”的产品限制。
2. Android 继续使用现有硬件采集与校准逻辑。
3. iOS 只需识别具体 iPhone 机型，按后台配置的机型算力范围完成校准，不要求提供 Android 的 SoC、GPU、内存字段。
4. 按机型匹配，不区分存储容量、颜色、地区 SKU。例如不同容量的 iPhone 16 Pro 共用一条规则。
5. 预设目录覆盖从 iPhone 6 / iPhone 6 Plus 开始，所有已经发布并销售过的 iPhone，包括各代 SE、mini、Plus、Pro、Pro Max 等，不能只包含目前在售机型。
6. 当前方案记录了 47 个机型的目录快照。实施时重新核对 [Apple 官方机型目录](https://support.apple.com/en-us/108044)，修正遗漏或错误，不把数字 47 当作永久约束，不加入未经核实或尚未销售的型号。
7. 所有算力范围都是“运营预设值”，不是 Apple 官方性能、真实压测结果或收益承诺。iPhone 16 Pro 的 100–120 是用户提供的示例。
8. 运营者可以查询、新增、修改、停用、删除机型规则，以及维护范围和经过核验的机型别名。
9. 清理前端各入口的 Android 独占提示；对于实际尚未具备的能力，不能展示可成功执行的假入口。
10. H5 保留查看状态和打开 App 的引导，不执行原生手机采集、校准、激活、心跳或任务。

## 三、先核对当前实现，再按方案落地

涉及工程：

| 工程 | 用途 |
| --- | --- |
| `nexion-frontend-uniapp` | 正式 App |
| `nexion-backend` | 后端 |
| `nexion-frontend-pc` | 运营后台 |
| `nexion-frontend-prototype` | H5 镜像 |

不要凭本地目录名称判断工程身份。先核对 remote、branch、HEAD、工作区状态，保护已有 WIP。

上次检查发现的关键缺口，需在最新代码中复核：

- App 的 `native-phone-runtime.ts`、`device-signals.ts` 及登录、校准、设备管理相关门控仍偏向 Android。
- 后端虽接受 `ios` 平台，但匹配仍要求硬件字段，规则只有固定 `computeValue`。
- 后台已有 E6 手机规则管理及 A2 审批流程，但缺少 iPhone 机型区间管理。
- 激活复核目前依赖固定算力值，需要与新的持久化结果一致。

不能只替换文案或把平台判断增加 `ios` 就宣称完成。

## 四、后端实现要求

1. 按方案引入独立的 iOS 机型范围规则，保留 Android 原有字段校验和匹配行为。
2. 支持规范机型、已核验别名、上下限、启停状态和运营预设来源。
3. 精确匹配机型，禁止按“包含 Pro”等方式猜型号。通称 iPhone、空机型、未知机型不能授予算力。
4. 最终算力由服务端在有效范围内分配并保存，前端不能自行生成或提交最终值。
5. 按方案实现首次成功校准分配一次；重复请求、刷新、重新登录和同机恢复读取已有结果，不能换一个幂等键就重新抽值。
6. 保存规则编号、版本、范围、最终值、机型和安装绑定等必要快照。
7. 匹配、后台试算、GET、影响预览和激活复核不得重新抽取随机值。
8. 激活使用已保存的结果完成复核，保持现有安装绑定、换机、槽位、事务和版本约束。
9. 规则更新、停用或删除不重写已激活设备的结果，不修改历史结算。
10. 兼容旧配置和旧结果，优先复用现有存储；只有确有需要才增加迁移。
11. 单位按方案沿用 `computeUnit=platform`，展示“平台算力 / 运营预设”，不要把预设值包装成物理 TOPS 或 TOPS/s。

## 五、运营后台要求

复用现有 E6 管理与 A2 审批链，不新建绕过审批的直接发布入口。

实现：

- iPhone 机型列表、搜索、筛选。
- 新增、编辑、停用和删除。
- 上下限、精度、重复机型和别名冲突的校验。
- 完整预设目录的载入和导入预览。
- 重复导入只补缺失，不覆盖运营者修改的范围、别名或停用状态。
- iOS 试算只需机型，展示匹配范围及可能档位，不生成用户校准记录。
- A2 展示新增、修改、删除、停用及范围前后差异。
- 发布、版本冲突、失败恢复和 GET 回读。

预设资源随代码交付；载入预设先进入草稿，经过现有审批流程才生效。不要因为代码中已有 JSON 就宣称后台正式配置已经生效。

## 六、App 与 UI 要求

1. 核验当前 uni-app / 原生 SDK 实际返回的机型信息。必要时建立经过验证的硬件标识符到规范机型映射，不能使用用户可编辑的设备昵称或浏览器 UA 猜测机型。
2. iOS 显示“识别机型 → 匹配运营规则 → 校准结果 → 激活确认”的真实过程。
3. 显示识别机型、运营预设范围、保存后的算力和实际状态。
4. 不展示没有执行过的 GPU 压测、真实跑分或无限后台计算承诺。
5. 检查登录恢复、首次设置、校准页、设备仓库、赚取页、相关引导和所有现有语言，清理不再成立的 Android 独占提示。
6. H5 的原生执行限制必须在实际逻辑中保持，不能只隐藏按钮。
7. 检查 320px 小屏、长机型名、明暗主题和现有语言，避免文字溢出、操作按钮过大。
8. 目录包含 iPhone 6 不代表当前安装包能运行于它支持的旧 iOS。核对最低系统版本和 SDK 兼容性，准确记录不能支持的部分，不用预设存在冒充真机可运行。

## 七、实施顺序和验收

按方案 S1–S5 推进：后端规则 → 校准持久化 → 运营后台 → App → H5 同步与联调。

完整落实方案中的 I01–I21 验收，重点证明：

- 同机型不同容量命中同一规则。
- iOS 无 SoC/GPU/RAM 也可按机型校准。
- 未知机型无算力、激活或收益副作用。
- 重试、并发、重登不会反复抽值。
- 激活、设备列表和服务端回读一致。
- 试算及 GET 不产生分配记录。
- 规则停用或删除保留历史结果。
- 导入不会覆盖运营修改。
- Android 原有流程不退化。
- H5 不能通过伪装平台或直达路由执行原生操作。
- 后台 CRUD、审批和发布有真实交互及接口回读证据。

运行与改动相关的测试、构建和仓库要求的检查。原生构建、模拟数据测试、真机测试分别报告；没有 iPhone 真机环境时明确列为未验证，不能写“全部通过”。
