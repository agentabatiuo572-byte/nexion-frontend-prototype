# Android 手机算力按芯片校准（浮动区间）方案

日期：2026-10-28。状态：**方案决定已确认（见 §9），功能待实施、待验证**。前置：[iPhone 机型区间校准](2026-10-27-ios-model-calibration.md)、[机型一致性风控](2026-10-28-iphone-model-risk-control.md)（代码见 `test`；配置发布、部署和真机状态以各自实施记录为准）。

## 1. 已确认的决定（2026-10-28）

1. **Android 按芯片报算力**，不按单个机型。
2. **算力做浮动区间**，与 iPhone 一致：首次校准成功时服务端在区间内抽一次并保存，之后重试、重新登录、重装都读回原值。
3. **预置近 5 年主流芯片**。
4. **内存不参与**：同一芯片不分内存档。
5. **Android 与 iPhone 统一使用模糊文案**：不出现「识别机型」「识别处理器」这类说法，校准中只显示「算力校验中…」，结果只显示算力值及档位，不显示芯片或机型名称。
6. **六档初始区间按第 2 节执行**，区间已确认，芯片标识仍须按匹配规则核验。
7. **旧的 Android 硬件规则直接停用**：项目还没上线，不保留后备。
8. **App 尚在开发阶段，未上线**：后端、App 和后台同轮更新合同并使用新测试包，不维护旧版 App 接口兼容，不增加历史绑定迁移方案。
9. **同一安装改报不同规范芯片就拦截，由客服解除**；同芯片别名切换、运营移档和改名不构成芯片变化。

## 2. 最简方案：6 个芯片档，每档一条规则

**结论**：把芯片分成 6 个性能档，**每档一条规则、一个区间**；同一芯片的全部别名作为一个组，整体归档和移动。芯片身份、运营性能档、结果 T1–T5 是三个不同概念。

| 比较项 | 每颗芯片一条规则 | 每档一条规则（采用） |
|---|---|---|
| 运营维护 | 每个芯片型号一条规则、一个区间 | 6 条规则、6 个区间 |
| 调整算力 | 逐条改 | 改一档，这一档的所有芯片一起生效 |
| 新芯片上市 | 新增一条规则，填区间 | 核实芯片及其别名，整组加入对应档 |
| 待核验样本处理 | 新建规则 | 核实标识归属后选择芯片与档 |
| A2 审批差异 | 改动分散，难核对 | 改动集中，容易核对 |
| 配置大小 | 重复字段较多，需实测 | 重复字段较少；仍须测完整配置的 UTF-8 字节数，不预先断言低于 60 KB |
| 单颗芯片特殊处理 | 直接改 | 将芯片及全部别名整体移到新建规则，芯片编号不变 |

后台按芯片名称、厂商和别名显示。预设目录提供已核验的芯片组和来源；实际匹配使用已发布配置，App 和用户侧不显示芯片名称。

**已确认的 6 档初始区间**（平台算力点，与 iPhone 刻度对齐：iPhone 17 Pro Max 为 125–145，iPhone 11 为 45–60）：

| 档位 | 已确认初始区间 | 包含的芯片 |
|---|---:|---|
| 旗舰 | 115–140 | 骁龙 8 Elite Gen 5、骁龙 8 Elite、天玑 9500、天玑 9400 / 9400+ |

| 高端 | 75–95 | 骁龙 8 Gen 1、骁龙 8+ Gen 1、骁龙 8s Gen 3、骁龙 7+ Gen 3、天玑 9000 / 9000+、天玑 8400、天玑 8300、Tensor G4、Tensor G3 |
| 中端 | 55–75 | 骁龙 888 / 888+、骁龙 870、骁龙 7+ Gen 2、骁龙 7 Gen 3、骁龙 7 Gen 1、骁龙 7s Gen 3、骁龙 778G / 778G+ / 782G、天玑 8200、天玑 8100、天玑 1200、天玑 7200、Exynos 2200、Exynos 2100、Exynos 1580、Tensor G2、Tensor（第一代） |
| 中低端 | 38–55 | 骁龙 7s Gen 2、骁龙 6 Gen 1、骁龙 6s Gen 3、骁龙 695、天玑 7300、天玑 7050 / 7025、天玑 1080、天玑 920 / 900、天玑 6300 / 6100+ / 6080、天玑 810 / 700、Helio G99、Exynos 1480、Exynos 1380、Exynos 1330 / 1280、紫光展锐 T820 |

- 共 82 个芯片型号（含加强版和兄弟型号）。2026 年新发布的芯片在实施时按官方发布情况补入。
- 骁龙 888、Exynos 850、SC9863A、Helio G85 发布于 2020 年或更早，但 2021 年后仍是大量主流机型的芯片，所以收入。
- 华为麒麟不收入：鸿蒙 NEXT 不能运行 Android 安装包，App 已对鸿蒙标记为不支持。
- 区间是运营预设值，不代表厂商指标或实测跑分。档与档的区间首尾相接，同一档内的抽值可能跨 T1–T5 档位分界，档位以抽到的值为准，与 iPhone 一致。
- **共享代号不能直接分档**：天玑 6020 与 700 均有 `MT6833` 的官方设备资料（[OPPO A79](https://www.oppo.com/ro/smartphones/series-a/a79-5g/specs/)、[Dorland Extreme_5G 规格第 3 页](https://www.dorland-tech.cn/en/Uploads/20220323/27f51408b1806ebc9263f3aec1a3136a.pdf)）。上表区间已确认，不代表仅凭 `MT6833` 能区分两者。预设须附已知歧义代号清单；未有唯一识别依据的代号不得加入匹配别名，仅收到它时待核验。不得为消除识别歧义擅自改变已确认分档；后续调整仍走运营审批。

## 3. 匹配设计

### 3.1 芯片标识的读取

App 读取以下标识，全部上报；服务端检查全部有效标识后作唯一判断，不采用「先匹配到谁就返回谁」：

1. `Build.SOC_MODEL`（Android 12+），例如高通 `SM8550`、联发科 `MT6985`。
2. 系统属性 `ro.soc.model`、`ro.board.platform`，例如高通平台代号 `kalama`、联发科 `mt6985`。Android 11 及以下靠这一项。
3. `Build.HARDWARE`，例如联发科机型常见的 `mt6768`；高通机型通常只返回 `qcom`，无法区分。

服务端与 iPhone 一样做规范化和精确别名匹配，不做模糊匹配。`qcom`、`unknown` 这类通称不能指向任何档。每个芯片代号和平台名在实施时按两个独立来源核对（厂商官方产品页和一个独立的设备规格库），只有一个来源的先不收录。

- 先规范化、去重，排除空值、通称和已知歧义代号。剩余标识全部解析；只有一个芯片身份时才检查其所属档是否启用。
- 多个已知标识指向不同芯片时，统一为 `SOC_CONFLICT`，即使同档也不通过；不能靠调换顺序或另一个启用档绕过冲突。指向同一芯片的不同别名可通过。
- 未识别或歧义标识不能独立授权匹配；另有唯一、已核验的明确标识时可据此匹配，原始标识保留服务端诊断。空值/通称以外无可用命中时按 `SOC_UNKNOWN` 待核验。
- Android 11 及以下的属性读取是待真机验证的能力，不保证可用；读取失败仍走待核验，不猜测芯片。

### 3.2 规则字段

`androidSocRules` 列表放进现有手机算力规则（`E.compute.phoneCalibration.policy`），每条：

```
id, name（性能档名，例如「旗舰」）, minComputeValue, maxComputeValue,
enabled, valueSource=OPERATOR_PRESET, note,
chips[]: { socKey（稳定芯片编号）, name, manufacturer, aliases[] }
```

- 档规则编号、芯片编号均稳定且唯一；改名、移档不换编号。一个芯片只能属于一个档，同一芯片的别名不得拆散到不同档。
- 规范化后的别名在全部芯片间唯一；通称、已知歧义代号禁止发布为匹配别名。服务端统一校验，后台只提供即时反馈。
- Android 每档全部芯片组的别名合计最多 100 个，不顺带扩大 iPhone 限制；数值沿用正数、最多两位小数、上下限合法等既有校验，并检查含 iPhone 规则的整份配置字节上限。

### 3.3 待核验

| 情况 | 原因（只在后台显示） |
|---|---|
| 一个标识都读不到，或只读到通称 | `SOC_MISSING` |
| 读到了但不在任何档 | `SOC_UNKNOWN` |
| 所在档已停用 | `SOC_DISABLED` |
| 多个已知标识指向不同芯片 | `SOC_CONFLICT` |
| 同一安装改报不同规范芯片，客服尚未解除锁定 | `SOC_CHANGED` |

不分配算力。App 显示现有待核验页，保留重新校准、联系客服和暂不激活出口。后台按「规范芯片或未识别代号 × 原因」汇总，可查看同次请求的全部标识；冲突样本不得拆成多个可直接授权的单代号。运营核实来源后，将唯一别名加入已有芯片组或新建芯片组，再走 A2；不能仅凭客户端样本认定芯片。发布后用户重新校准，不自动激活。

### 3.4 浮动区间与抽值

完全复用 iPhone 的做法：

- 安全随机数抽两位小数，按「账号 + 稳定性能档规则编号」保存，不使用档位名称或 T1–T5 作为复用键。
- 同一账号同一档的值仍在当前区间内就复用；来回换报也读回原值。
- 激活复核检查保存值仍在区间内、档位一致。
- 区间只留在服务端，返回 App 的出口统一去掉。
- 继承账号行锁、幂等和事务约束；并发请求只分配一次。试算、GET、影响预览和激活复核均不抽值。规则发布不重写已激活设备及历史结算；待激活结果遇到规则变化，须重新校准后按当前档复用或分配。

同一档内的不同芯片共用一个抽值（按档复用）。同档芯片性能接近，换到同档的另一台手机也保持原值，与 iPhone 同机型换容量的处理一致。

### 3.5 旧硬件规则停用

- 删除「芯片 + 显卡 + 内存 → 固定值」的 Android 硬件规则匹配，Android 只按芯片档匹配。
- E6 去掉「Android 硬件规则」编辑区和相关试算字段（显卡、内存）。
- 开发环境切换新配置时移除旧硬件规则字段；本轮专用旧测试样本重新校准，不为未上线版本建设兼容读取或历史迁移。
- Android 绑定使用「平台 + 规范化机型 + 稳定芯片编号」，继续结合现有安装编号判断；不含 GPU、性能档、T1–T5、规则版本或算力值。芯片移档、改名、别名切换不构成换机，不消耗换机次数或重置绑定时间；真实换安装仍走既有换机流程。

## 4. 风控

- 已有的「同一手机换报机型」（上线即拦截）和「同一账号报多个机型」照常适用于 Android，按 `Build.MODEL` 判断。
- **已确认：同安装改报芯片立即拦截，由客服解除**。同一账号、同一安装首次成功识别后记录稳定芯片编号；后续改报不同芯片在抽值前进入待核验，不分配算力、不允许激活。重试、换幂等键或重新登录不能自动解除。同芯片别名切换、运营移档和改名不拦；未知转已知不以旧原始字符串误判。客服解除沿用既有权限、确认、理由和审计，机型解锁入口同步支持本次芯片锁；解除后下次成功校准锁定新芯片，不能退回旧锁。首次就完整伪造硬件不在此检查的可识别范围。
- **本步不新增「芯片与显卡不符」检查**，保持简单。需要时可以在后续步骤里按芯片代号前缀推断厂商来做。

## 5. 用户侧（App）

- **Android / iPhone 校准中**：统一只显示「算力校验中…」，不出现「识别机型」「识别处理器」「硬件检测」等说法，也不显示步骤里的「识别」字样。
- **校准成功**：只显示「算力预估 93.48 · T4」和激活按钮，不显示芯片或机型名称。
- **待核验**：沿用现有页面和文案。
- 三语文案同步；样式沿用现有液态玻璃卡片和主题色。
- **iPhone 同步修改**：移除「正在识别机型…」、步骤「识别机型」和「您的机型是 iPhone 16 Pro」等旧文案，统一采用上述校准中及结果文案，覆盖三语。此决定覆盖前置 iPhone 方案的旧展示要求；按机型识别与分配算力的内部逻辑不变。

## 6. E6 后台

- 新增「Android 芯片档」区，交互与 iPhone 机型区一致：
  - 6 条档位规则：区间、启停、说明；
  - 每档展开芯片及其全部别名；移档按芯片整组操作，别名只能在所属芯片内增删，不能单独移到另一档；
  - 载入芯片预设：预览新增、跳过、冲突和已移除项，不覆盖已改区间、启停或归属。配置保存主动移除的预设芯片编号/别名记录，重复导入默认跳过；需要恢复时单列并由运营明确勾选，再走 A2，不把主动删除当作从未导入；
  - 草稿与已发布的差异。
- 试算：可逐条添加本次读取的多个标识，按正式匹配逻辑显示芯片、性能档、区间、可能 T1–T5 或待核验原因，不要求单框多值输入。
- 待核验样本按 §3.3 处理；空列表、加载、字段冲突、提交失败保留明确反馈与重试/取消出口。
- A2 审批页显示区间前后值、芯片整体移档、别名增删、主动删除项恢复；继续沿用权限、理由、双人审批、版本冲突与发布读回规则。

## 7. 数据与接口

- Android 校准请求统一使用 `socIds[]`；读取不到时传空数组。旧 `soc` 不再作为 Android 校准匹配输入，同轮更新 App 采集、后端请求模型、样本与试算。接收边界限制最多 4 项、每项最多 128 字符，原始内容仅在服务端保存。
- 服务端快照保存 `ANDROID_SOC_RANGE`、稳定芯片编号、性能档规则编号/版本、区间、来源和最终值；不把性能档混作设备身份。
- **展示与响应合同分开定义**：Android 界面只展示算力、T1–T5 和状态；响应保留现有流程需要的账号、设备、revision、激活状态、收益等字段。芯片名称、原始标识、区间、规则编号/版本、来源及风控锁不下发；现有 `signals` 等嵌套出口也须脱敏。
- Android 成功响应以 `calibrationMethod=ANDROID_SOC_RANGE` 区分结果类型，仅供解析、不在界面显示。App 解析器同步适配，不再强制 Android 结果持有服务端规则编号/版本；校准、GET、激活及回执使用同一投影合同。iPhone 字段按原合同处理，界面统一按 §5 隐去机型和识别过程。不能只改服务端删字段，也不保留旧测试包兼容分支。
- 后端、App、E6/A2 同轮更新并联调，统一安装新测试包；发布流程和测试数据重建在开发环境完成，不能将接口测试通过当作真机验收。

## 8. 验收场景

| 编号 | 场景 | 期望 |
|---|---|---|
| A01 | Android 12+ 读到 `SM8550` | 命中「次旗舰」档，在 95–115 内抽值并保存 |
| A02 | 同一账号重试、换幂等键、重新登录、重装 | 读回同一个值 |
| A03 | Android 11 只读到一个平台代号 | 经核验能唯一确定芯片才匹配；共享或未核验唯一性的代号（包括原稿直接采用的 `lahaina`）待核验，不按同档猜芯片身份 |

| A05 | 代号不在任何档 | 待核验 `SOC_UNKNOWN`；核实归属后加入芯片组，经 A2 发布，用户重试 |
| A06 | 所在档已停用 | 待核验 `SOC_DISABLED` |
| A07 | 调整某档区间，旧值仍在新区间内 | 不重新抽值；落在区间外才重新抽 |

| A11 | Android / iPhone 的校准中、步骤与结果页，三语 | 均不出现「识别机型 / 识别处理器」及芯片或机型名称；统一显示「算力校验中…」和算力值及档位 |
| A12 | 同一安装先报一个机型再报另一个 | 按「同一手机换报机型」拦截 |
| A13 | 开发环境切换新方案 | 配置与 E6 移除旧硬件规则，本轮测试样本重建，不增加旧规则回退或迁移逻辑 |
| A14 | 后端、App、E6/A2 同轮升级 | 统一用 `socIds` 和新响应合同；新测试包校准至激活读回闭合，不要求旧版 App 兼容 |
| A15 | E6 载入预设、调整档、试算、提交 A2、审批发布 | 发布后新校准生效，已激活的设备不变 |
| A16 | 仅上报共享代号 `MT6833` | 待核验，不任意归为天玑 700 或 6020；发布校验禁止将歧义代号直接指定给单颗芯片 |
| A17 | 多个标识命中不同芯片，或分属启用/停用档；反转输入顺序 | 均为 `SOC_CONFLICT`，不抽值；同一芯片不同别名则结果一致 |
| A18 | 芯片整体移档后，原手机使用不同别名重新校准并激活 | 全部别名命中新档，稳定芯片编号和绑定身份不变，不触发换机或消耗次数 |

| A20 | 删除预设芯片或别名并发布，再次载入预设 | 默认不恢复；明确勾选恢复后进入 A2 差异，未审批不生效 |

| A22 | 非法范围/重复别名/超大配置、审批冲突/失败/未来生效 | 边界校验和原审批规则生效；草稿可恢复，未发布内容不影响校准 |
| A23 | 新测试包在代表品牌、Android 12+ 与 11 及以下采集→校准→激活→重登 | 记录真实标识、系统/包版本和完整读回；读取失败有待核验出口；H5 仍不能执行原生校准或激活 |
| A24 | 芯片改报被拦后重试/重登，客服解除后再校准 | 解除前仍拦截；有权限的客服确认并填写理由后解除、留下审计；下次成功校准锁定新芯片，后续不恢复旧锁 |
