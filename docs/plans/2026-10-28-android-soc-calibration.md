# Android 手机算力按芯片校准（浮动区间）方案

日期：2026-10-28。状态：**方案待确认，未实现**。前置：[iPhone 机型区间校准](2026-10-27-ios-model-calibration.md)、[机型一致性风控](2026-10-28-iphone-model-risk-control.md)（均已上线 `test`）。

## 1. 目标与已确认的要求

1. **Android 按芯片（SoC）报算力**，不按单个机型。同一颗芯片的所有手机共用一条规则。
2. **算力做浮动区间**，与 iPhone 一致：每条芯片规则配一个运营预设区间，用户首次校准成功时由服务端在区间内抽一次并保存；重试、重新登录、重装都读回原值。
3. **预置近 5 年主流芯片目录**：覆盖 2021 年以来发布、在主流手机上大量使用的芯片，运营可以在此基础上增删改、停用。
4. 发布沿用现有 E6 编辑 → 试算 → A2 审批。用户界面延续「不暴露运营规则」：只显示处理器名称和本人的算力值。

## 2. 现状和要解决的问题

现在的 Android 规则是「平台 + 可选机型 + 芯片 + 显卡 + 内存区间 → 固定算力值」，存在四个问题：

| 问题 | 影响 |
|---|---|
| 规则为空，也没有预设 | 不录规则，所有 Android 用户都进待核验 |
| 芯片只读 `Build.SOC_MODEL`，Android 12 起才有 | Android 11 及以下读不到芯片，直接待核验 |
| 芯片和显卡都要求字面完全一致 | 读到的是 `SM8550` 这类代号；显卡名称写法不统一，容易匹配失败 |
| 算力是固定值 | 没有浮动效果 |

## 3. 匹配设计

### 3.1 芯片规则

新增「Android 芯片规则」，每条规则包含：

| 字段 | 说明 |
|---|---|
| 规则编号 | 稳定 ID，例如 `soc-snapdragon-8-gen-2` |
| 芯片名称 | 显示用的规范名，例如「骁龙 8 Gen 2」，英文为 Snapdragon 8 Gen 2 |
| 厂商 | 高通 / 联发科 / 三星 / 谷歌 / 紫光展锐 |
| 已核验别名 | 系统能读到的芯片标识，见 3.2，每行一个 |
| 显卡系列 | 该芯片配套的显卡，例如 Adreno、Mali、Immortalis、Xclipse，只用于风控交叉核对 |
| 算力下限 / 上限 | 运营预设区间，最多 2 位小数，上下限相等即固定值 |
| 启用 / 停用、目录分类、运营说明 | 与 iPhone 规则一致 |

**不再要求显卡和内存参与匹配**：芯片基本决定了显卡，内存与 iPhone 不区分容量的处理一致（见第 10 节第 1 问）。

### 3.2 芯片标识的读取和别名

App 按以下顺序读取，取到第一个非空值，并把读到的所有标识都上报，服务端逐个尝试匹配：

1. `Build.SOC_MODEL`（Android 12+），例如高通 `SM8550`、联发科 `MT6985`。
2. 系统属性 `ro.soc.model`、`ro.board.platform`，例如高通平台代号 `kalama`、联发科 `mt6985`。
3. `Build.HARDWARE`，例如联发科机型常见的 `mt6768`；高通机型通常只返回 `qcom`，无法区分，按通称处理。

服务端与 iPhone 一样做规范化和精确别名匹配（不区分大小写、去多余空白），**不做模糊匹配**。`qcom`、`unknown` 这类通称不能指向任何芯片。

同一型号芯片的不同代号（例如加强版、不同批次）都写成同一条规则的别名。代号和平台名在实施时按两个独立来源核对；只有一个来源的先不收录，和 iPhone 标识符的处理方式相同。

### 3.3 待核验情况

| 情况 | 待核验原因 |
|---|---|
| 一个标识都读不到 | `SOC_MISSING` |
| 读到了但没有匹配的规则 | `SOC_UNKNOWN` |
| 匹配到的规则已停用 | `SOC_DISABLED` |

待核验不分配算力；App 显示现有的待核验页，原因统一为「待核验」，不告诉用户具体原因。后台待核验样本按「上报的芯片标识 × 原因」汇总，运营补规则或补别名后，用户重新校准即可。

### 3.4 浮动区间与抽值

完全复用 iPhone 的做法：

- 首次成功校准时，服务端在区间内用安全随机数抽一个两位小数并保存。
- 同一账号、同一芯片已有且仍在当前区间内的值优先复用：重试、重新登录、重装、来回换报都读回原值。
- 激活复核检查保存值仍在当前区间内、档位一致。
- 区间只留在服务端，App 只拿到芯片名称和本人的算力值。

### 3.5 旧的硬件规则

旧的「芯片 + 显卡 + 内存 → 固定值」规则停止新增，E6 隐藏「添加硬件规则」。已发布的旧规则继续生效，作为芯片规则匹配不到时的后备，直到运营删除；E6 给出提示。正式环境目前是否有旧规则，需要上线前查一次。

## 4. 风控衔接

- 已有的「同一手机换报机型」和「同一账号报多个机型」照常适用于 Android，按 `Build.MODEL` 判断。
- **新增「芯片与显卡不符」检查（Android）**：规则里的显卡系列和 App 读到的显卡对不上即命中，例如上报骁龙芯片、显卡却是 Mali。
  - 和其他检查一样可设「关闭 / 观察 / 拦截」，默认观察。
  - 显卡读不到或被系统遮蔽（例如只返回软件渲染器名称）时不判。
- 新增「同一手机换报芯片」：同一安装锁定第一次上报的芯片标识，与机型锁一起判断，处理方式沿用「同一手机换报机型」的设置。

## 6. 数据结构

**芯片规则**放进现有手机算力规则（`E.compute.phoneCalibration.policy`），新增 `androidSocRules` 列表：

```
id, name, vendor, aliases[], gpuFamilies[], minComputeValue, maxComputeValue,
enabled, valueSource=OPERATOR_PRESET, catalogClass, note
```

- 与 iPhone 规则共用一套编号唯一性和名称唯一性校验，上限 500 条。
- **存储上限要先处理**：这条配置的上限是 60 KB。
  - 现有 47 条 iPhone 规则（含设备信息）实测约 16.8 KB，约 63 条芯片规则估计 14 KB，合计约 31 KB。
  - 有定时发布时，当前和待生效两份同时存，约 62 KB，会超限。
  - 建议实施时先把这一配置的存储字段扩大（一次数据库迁移），保持「整份规则一起审批、一起发布」不变。

**校准请求**新增可选的 `socIds[]`，即 3.2 读到的全部标识。现有的 `soc` 字段保留，旧版 App 只传它也能匹配。

**校准结果（服务端快照）**：

- 新增 `calibrationMethod=ANDROID_SOC_RANGE`、`soc`（芯片规范名）、区间和来源。
- 区间、来源和抽值记录都只留在服务端，在返回 App 的出口统一去掉。
- 返回 App 的只有：芯片名称、算力值、档位。

**硬件标识**：Android 的绑定标识改为「平台 + 机型 + 芯片规范名」，不再包含显卡名称，避免显卡读法变化被误判为换机。

## 7. App 改动

- `device-signals.ts` 的 Android 分支按 3.2 读取芯片标识并上报 `socIds`。读取失败的项跳过，不猜测。
- 校准结果的显示复用 iPhone 的结果卡，内容为处理器名称和算力值，例如「您的处理器是 骁龙 8 Gen 2 · 算力预估 93.48」。**文案需要你确认**（第 10 节第 2 问），样式沿用现有液态玻璃卡片和主题色。
- 待核验页沿用现有页面和文案。
- 三语文案同步；H5 不做校准，只同步文案。

## 8. E6 后台

- 新增「Android 芯片规则」区，交互与 iPhone 机型区一致：
  - 搜索（名称或别名）、按厂商和状态筛选、新增、编辑、停用、删除；
  - 载入芯片预设（只补缺失的芯片，不覆盖运营已改的内容）；
  - 草稿与已发布的差异。
- 试算：Android 只需填芯片标识，可选填显卡，显示命中的芯片、区间、可能档位和风控命中项。
- 待核验样本按「芯片标识 × 原因」显示。运营可以从样本直接为某条规则补别名，补完仍需走 A2 才生效。
- A2 审批页显示芯片规则的新增、修改、停用、删除和区间前后对比。
- 机型风控区新增「芯片与显卡不符」一项。

## 9. 验收场景

| 编号 | 场景 | 期望 |
|---|---|---|
| A01 | Android 12+ 读到 `SM8550`，规则有该别名 | 命中骁龙 8 Gen 2，在区间内抽值并保存 |
| A02 | 同一账号重试、换幂等键、重新登录、重装 | 读回同一个值 |
| A03 | Android 11 读不到 `SOC_MODEL`，读到平台名 `lahaina` | 经别名命中骁龙 888 |
| A04 | 只读到 `qcom` | 待核验 `SOC_MISSING`，不分配算力 |
| A05 | 读到的代号不在任何规则里 | 待核验 `SOC_UNKNOWN`，出现在后台样本中 |
| A06 | 规则已停用 | 待核验 `SOC_DISABLED` |
| A07 | 调整区间后，旧值仍在新区间内 | 不重新抽值；落在区间外才重新抽 |
| A08 | 激活复核 | 保存值在区间内且档位一致才能激活 |
| A09 | 骁龙芯片配 Mali 显卡；该检查设为拦截 | 待核验，原因不告诉用户 |
| A10 | 显卡读不到 | 不判「芯片与显卡不符」 |
| A11 | 同一安装先报 `SM8550` 后报 `SM8650` | 按「同一手机换报机型」的设置处理 |
| A12 | App 收到的校准结果、激活返回和回执 | 只有芯片名称、算力值和档位，没有区间和规则 |
| A13 | 已发布的旧硬件规则 | 芯片规则匹配不到时仍按旧规则匹配；E6 不再允许新增 |
| A14 | 只传 `soc`、不传 `socIds` 的旧版 App | 按 `soc` 匹配 |
| A15 | E6 载入预设、编辑、试算、提交 A2、审批发布 | 发布后新校准生效，已激活的设备不变 |

## 10. 待你确认的问题

1. **内存是否参与**：建议不参与，同一芯片不分内存档，与 iPhone 不分容量一致。如果要区分（例如 8GB 和 12GB 的区间不同），每条芯片规则改为按内存分档，运营维护量会翻倍。
2. **App 结果文案**：
   - Android 的校准结果是显示「您的处理器是 骁龙 8 Gen 2」（建议，系统机型名常是 `SM-S911B`、`2201123G` 这类代号，用户看不懂），还是显示机型？
   - 「识别中」步骤的文字沿用 iPhone 的三步，把「识别机型」改为「识别处理器」，是否可以？
3. **区间草案**：第 5 节的分档和数值是否按此作为初始预设？要整体上调或下调，告诉我比例即可。
4. **旧硬件规则**：按 3.5 停止新增、保留已发布的作为后备（建议），还是上线时直接停用？

## 11. 工作量与边界

- 后端约 2–3 天：芯片规则、匹配、抽值复用、激活复核、风控新检查、样本汇总、接口和测试。
- E6 约 1.5–2 天。
- App 约 1 天：芯片标识读取、结果卡、三语文案，原型 H5 同步文案。
- 芯片目录核验约 1–1.5 天。
- 合计约 6–7 个工作日，不含真机验收。
- 真机要核实：`SOC_MODEL` 和系统属性在主流品牌上的实际返回值（三星、小米、OPPO、vivo、realme、传音等），以及 Android 11 及以下能否读到系统属性。
