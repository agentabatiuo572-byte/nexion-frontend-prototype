# Android 手机算力按芯片校准（浮动区间）方案

日期：2026-10-28。状态：**方案已按确认的决定修订，待确认后实施**。前置：[iPhone 机型区间校准](2026-10-27-ios-model-calibration.md)、[机型一致性风控](2026-10-28-iphone-model-risk-control.md)（均已上线 `test`）。

## 1. 已确认的决定（2026-10-28）

1. **Android 按芯片报算力**，不按单个机型。
2. **算力做浮动区间**，与 iPhone 一致：首次校准成功时服务端在区间内抽一次并保存，之后重试、重新登录、重装都读回原值。
3. **预置近 5 年主流芯片**。
4. **内存不参与**：同一芯片不分内存档。
5. **用户侧文案尽量模糊**：不出现「识别机型」「识别处理器」这类说法，校准中只显示「算力校验中…」，结果只显示算力值，不显示芯片或机型名称。
6. **区间按最简单的方案**，见第 2 节。
7. **旧的 Android 硬件规则直接停用**：项目还没上线，不保留后备。

## 2. 最简方案：6 个芯片档，每档一条规则

**结论**：不按芯片逐条维护，而是把芯片分成 6 个性能档，**每档一条规则、一个区间**；芯片代号作为这一档规则的别名。

| 比较项 | 每颗芯片一条规则 | 每档一条规则（采用） |
|---|---|---|
| 运营维护 | 约 63 条规则、63 个区间 | 6 条规则、6 个区间 |
| 调整算力 | 逐条改 | 改一档，这一档的所有芯片一起生效 |
| 新芯片上市 | 新增一条规则，填区间 | 把代号加进对应档的别名 |
| 待核验样本处理 | 新建规则 | 点选「加入某档」 |
| A2 审批差异 | 改动分散，难核对 | 改动集中，容易核对 |
| 配置大小 | 与 iPhone 规则合计会超过 60 KB 上限，要先扩容 | 约 3 KB，不用改存储 |
| 单颗芯片特殊处理 | 直接改 | 把它的代号移到新建的一条规则里即可，结构不变 |

后台仍按芯片显示名称，运营看得懂。预设目录附带一份「代号 → 芯片名称、厂商」对照表，只在 E6 显示用；App 和用户侧不显示芯片名称。

**6 个档的区间草案**（平台算力点，与 iPhone 刻度对齐：iPhone 17 Pro Max 为 125–145，iPhone 11 为 45–60）：

| 档位 | 区间草案 | 包含的芯片 |
|---|---:|---|
| 旗舰 | 115–140 | 骁龙 8 Elite Gen 5、骁龙 8 Elite、天玑 9500、天玑 9400 / 9400+ |
| 次旗舰 | 95–115 | 骁龙 8 Gen 3、骁龙 8s Gen 4、骁龙 8 Gen 2、天玑 9300 / 9300+、天玑 9200 / 9200+、Exynos 2500、Exynos 2400、Tensor G5 |
| 高端 | 75–95 | 骁龙 8 Gen 1、骁龙 8+ Gen 1、骁龙 8s Gen 3、骁龙 7+ Gen 3、天玑 9000 / 9000+、天玑 8400、天玑 8300、Tensor G4、Tensor G3 |
| 中端 | 55–75 | 骁龙 888 / 888+、骁龙 870、骁龙 7+ Gen 2、骁龙 7 Gen 3、骁龙 7 Gen 1、骁龙 7s Gen 3、骁龙 778G / 778G+ / 782G、天玑 8200、天玑 8100、天玑 1200、天玑 7200、Exynos 2200、Exynos 2100、Exynos 1580、Tensor G2、Tensor（第一代） |
| 中低端 | 38–55 | 骁龙 7s Gen 2、骁龙 6 Gen 1、骁龙 6s Gen 3、骁龙 695、天玑 7300、天玑 7050 / 7025、天玑 1080、天玑 920 / 900、天玑 6300 / 6100+ / 6080、天玑 810 / 700、Helio G99、Exynos 1480、Exynos 1380、Exynos 1330 / 1280、紫光展锐 T820 |

- 共 82 个芯片型号（含加强版和兄弟型号）。2026 年新发布的芯片在实施时按官方发布情况补入。
- 骁龙 888、Exynos 850、SC9863A、Helio G85 发布于 2020 年或更早，但 2021 年后仍是大量主流机型的芯片，所以收入。
- 华为麒麟不收入：鸿蒙 NEXT 不能运行 Android 安装包，App 已对鸿蒙标记为不支持。
- 区间是运营预设值，不代表厂商指标或实测跑分。档与档的区间首尾相接，同一档内的抽值可能跨 T1–T5 档位分界，档位以抽到的值为准，与 iPhone 一致。

## 3. 匹配设计

### 3.1 芯片标识的读取

App 读取以下标识，全部上报，服务端逐个尝试：

1. `Build.SOC_MODEL`（Android 12+），例如高通 `SM8550`、联发科 `MT6985`。
2. 系统属性 `ro.soc.model`、`ro.board.platform`，例如高通平台代号 `kalama`、联发科 `mt6985`。Android 11 及以下靠这一项。
3. `Build.HARDWARE`，例如联发科机型常见的 `mt6768`；高通机型通常只返回 `qcom`，无法区分。

服务端与 iPhone 一样做规范化和精确别名匹配，不做模糊匹配。`qcom`、`unknown` 这类通称不能指向任何档。每个芯片代号和平台名在实施时按两个独立来源核对（厂商官方产品页和一个独立的设备规格库），只有一个来源的先不收录。

### 3.2 规则字段

`androidSocRules` 列表放进现有手机算力规则（`E.compute.phoneCalibration.policy`），每条：

```
id, name（档位名，例如「旗舰」）, aliases[]（芯片代号）, minComputeValue, maxComputeValue,
enabled, valueSource=OPERATOR_PRESET, note
```

- 与 iPhone 规则共用编号唯一和名称唯一的校验：一个代号只能属于一个档。
- 每条规则的别名上限从 20 提高到 100。

### 3.3 待核验

| 情况 | 原因（只在后台显示） |
|---|---|
| 一个标识都读不到，或只读到通称 | `SOC_MISSING` |
| 读到了但不在任何档 | `SOC_UNKNOWN` |
| 所在档已停用 | `SOC_DISABLED` |

不分配算力。App 显示现有的待核验页，原因统一为「待核验」。后台待核验样本按「芯片代号 × 原因」汇总，并按对照表显示芯片名称；运营可以从样本直接把代号加进某一档，加完仍走 A2 审批才生效。

### 3.4 浮动区间与抽值

完全复用 iPhone 的做法：

- 安全随机数抽两位小数，按「账号 + 档」保存。
- 同一账号同一档的值仍在当前区间内就复用；来回换报也读回原值。
- 激活复核检查保存值仍在区间内、档位一致。
- 区间只留在服务端，返回 App 的出口统一去掉。

同一档内的不同芯片共用一个抽值（按档复用）。同档芯片性能接近，换到同档的另一台手机也保持原值，与 iPhone 同机型换容量的处理一致。

### 3.5 旧硬件规则停用

- 删除「芯片 + 显卡 + 内存 → 固定值」的 Android 硬件规则匹配，Android 只按芯片档匹配。
- E6 去掉「Android 硬件规则」编辑区和相关试算字段（显卡、内存）。
- 已存的配置里如果还带旧规则字段，读取时忽略，下次发布时不再写入。
- 「芯片 + 显卡」不再参与绑定标识：Android 的绑定标识改为「平台 + 机型 + 档」，避免显卡读法变化被误判为换机。

## 4. 风控

- 已有的「同一手机换报机型」（上线即拦截）和「同一账号报多个机型」照常适用于 Android，按 `Build.MODEL` 判断。
- **本步不新增「芯片与显卡不符」检查**，保持简单。需要时可以在后续步骤里按芯片代号前缀推断厂商来做。

## 5. 用户侧（App）

- **校准中**：只显示「算力校验中…」，不出现「识别机型」「识别处理器」「硬件检测」等说法，也不显示步骤里的「识别」字样。
- **校准成功**：只显示「算力预估 93.48 · T4」和激活按钮，不显示芯片或机型名称。
- **待核验**：沿用现有页面和文案。
- 三语文案同步；样式沿用现有液态玻璃卡片和主题色。
- **iPhone 现状**（见第 9 节第 1 问）：校准中显示「正在识别机型…」，步骤里有「识别机型」，结果写「您的机型是 iPhone 16 Pro」。

## 6. E6 后台

- 新增「Android 芯片档」区，交互与 iPhone 机型区一致：
  - 6 条档位规则：区间、启停、说明；
  - 每档展开显示芯片列表（代号 + 对照表中的芯片名称），可以把代号移到别的档或移除；
  - 载入芯片预设：只补缺失的档和代号，不覆盖运营已改的区间和归属；
  - 草稿与已发布的差异。
- 试算：Android 只填芯片代号，显示命中的档、区间和可能档位。
- 待核验样本：按「代号 × 原因」显示，可以直接「加入某档」。
- A2 审批页显示各档区间前后对比和代号增删。

## 7. 数据与接口

- 校准请求新增可选的 `socIds[]`（第 3.1 节读到的全部标识）；现有的 `soc` 字段保留，只传它也能匹配。
- 校准结果（服务端快照）：`calibrationMethod=ANDROID_SOC_RANGE`、档位规则编号、区间和来源。区间和来源只留在服务端。
- 返回 App 的只有算力值、档位和状态，不含芯片名称。

## 8. 验收场景

| 编号 | 场景 | 期望 |
|---|---|---|
| A01 | Android 12+ 读到 `SM8550` | 命中「次旗舰」档，在 95–115 内抽值并保存 |
| A02 | 同一账号重试、换幂等键、重新登录、重装 | 读回同一个值 |
| A03 | Android 11 只读到平台代号 `lahaina` | 经别名命中对应档 |
| A04 | 只读到 `qcom` | 待核验 `SOC_MISSING`，不分配算力 |
| A05 | 代号不在任何档 | 待核验 `SOC_UNKNOWN`，出现在后台样本，可加入某档 |
| A06 | 所在档已停用 | 待核验 `SOC_DISABLED` |
| A07 | 调整某档区间，旧值仍在新区间内 | 不重新抽值；落在区间外才重新抽 |
| A08 | 同一账号换到同档的另一台手机 | 沿用原值 |
| A09 | 激活复核 | 保存值在区间内且档位一致才能激活 |
| A10 | App 收到的校准结果、激活返回和回执 | 只有算力值、档位和状态，没有芯片名称、区间和规则 |
| A11 | 校准中和结果页的文案 | 不出现「识别机型 / 识别处理器」，只显示「算力校验中…」和算力值 |
| A12 | 同一安装先报一个机型再报另一个 | 按「同一手机换报机型」拦截 |
| A13 | 已存配置带旧硬件规则字段 | 读取忽略，下次发布不再写入；E6 没有旧硬件规则编辑区 |
| A14 | 只传 `soc`、不传 `socIds` 的旧版 App | 按 `soc` 匹配 |
| A15 | E6 载入预设、调整档、试算、提交 A2、审批发布 | 发布后新校准生效，已激活的设备不变 |

## 9. 待你确认的问题

1. **iPhone 是否一起改成模糊文案**：iPhone 现在显示「正在识别机型…」、步骤「识别机型」、结果「您的机型是 iPhone 16 Pro」，这些是你之前确认的文案。
   - 建议两个平台统一：校准中「算力校验中…」，结果只显示算力值。
   - 还是保留 iPhone 现状？
2. **6 个档的区间草案**：是否按第 2 节作为初始预设？

## 10. 工作量与边界

- 后端约 2 天：芯片档规则、匹配、按档抽值复用、激活复核、停用旧硬件规则、样本汇总、接口和测试。
- E6 约 1.5 天：档位区、代号归属调整、试算、样本「加入某档」。
- App 约 0.5–1 天：芯片标识读取、模糊文案、结果卡，原型 H5 同步文案。
- 芯片代号核验约 1 天。
- 合计约 5 个工作日，不含真机验收。不需要扩大存储，也不需要数据库迁移。
- 真机要核实：`SOC_MODEL` 和系统属性在主流品牌上的实际返回值（三星、小米、OPPO、vivo、realme、传音等），以及 Android 11 及以下能否读到系统属性。
