# G1 original staking command status

Authenticated USER only: `GET /api/stakes/open-status?tierKey=usdt30d&amountUsdt=20`, with the original `Idempotency-Key` header. Scope is derived from the authenticated user: `APP:G1_STAKING_OPEN:USER:<userId>`. Client scope, owner and environment parameters confer no authority.

The response contains only `status`, `stakingCommandProtocol: 1`, `sourceEnvironment: "PRODUCTION"`, and `runId: ""`. States are SUCCEEDED, FAILED, PROCESSING, UNKNOWN, NOT_FOUND and MISMATCH. This reads the retained idempotency row without claim, reset, expiry transition, response deserialization, risk check, matureDue, settlement, audit or outbox writes. It neither returns private errors nor historical wallet/receipt data.

Key is trimmed, required, and limited to 128 characters before amount parsing. Tier is limited to 32 characters and uses the existing POST normalization (trim, lowercase, remove underscores; usdt30d/usdt90d/usdt180d/usdt365d). Amount is limited to 64 characters; BigDecimal precision <= 32, scale between -12 and 18, and at most 12 integer digits. The original POST HALF_UP scale-6 amount must be positive and <= 999999999999.999999 (canonical DECIMAL(18,6)). Valid scientific notation such as `2e1` is accepted. This does not inspect current sale switches, minimum amounts or balances.

Hash remains SHA256 of UTF-8 Java record text, e.g. `OpenRequest[tierKey=usdt30d, amountUsdt=20.000000]` -> `ad5bc99b62ed3964ea77c7e780185c9532fa25a864586c6e91f91af8f9c4353a`. The POST contract/hash and retained FAILED retry semantics are unchanged.

The recovery button looks up the original local payload/key and sends only this GET. It never creates an intent or refreshes ordinary positions. Qualified SUCCEEDED/FAILED removes only that local lease after the same account, binding and sheet generation are verified; no historical recovery archive is created. Unknown, missing, mismatched, failed reads and stale responses retain the original key. Multiple old intents are resolved one at a time; corrupt pending storage blocks a new command. Current pool/balance/minimum changes cannot redirect recovery to a new amount or tier.

Closing the sheet preserves existing unresolved keys. A fresh command requires an empty pending-open registry and a one-use preparation owned by the store, including its original account epoch and fingerprint/key. Closing, changing the term/account/binding, unmounting, disclosure rejection or local store preflight failure before the financial API call retires only that matching fresh preparation. The store marks dispatch after all local preflights, immediately before calling the financial API. A dispatched unknown result remains fenced; NOT_FOUND never authorizes cleanup. An old persisted lease has no fresh preparation ownership and cannot be retired by cancellation. Neither risk ACK nor status GET auto-submits another stake. Ordinary `GET /api/stakes` still has maturity-update semantics and is outside this pure status operation.

Source/transport verification does not resolve any original public request or authorize deployment. Current original Samsung 20/30 and G7 100 requests are excluded from cleanup/test samples.

Cancelled definitely-unsent preparations retain their in-memory retirement proof when local storage writes fail. Refresh, a new preparation, or restoring the sheet retries exact-key cleanup for the current account without financial dispatch. Already-dispatched unknowns and reconstructed persisted intents remain fenced; this does not promise cross-restart recovery. Regression cases cover temporary write/read failure, old lease reuse, account/epoch changes and replacement keys (Bug #547).
