# 消息系统功能优化方案

## 目标与范围

以 5180 客服整合版为基线。右上角是全站消息总入口；人工服务浮标直接进入全屏消息中心的“服务”分区；两处读取相同服务端状态，不复制人工消息为系统通知。NOVA/AI 入口保持关闭。

基本事实：通知、人工会话、工单是三种已有数据对象，各自有服务端已读协议。消息数必须以服务端为准；打开总入口不能自动清空未读；钱款状态必须由真实业务状态变化产生，不能由前端推断。当前主要缺口是通知分页后误减未读、工单未聚合、通知缺前台刷新、充值/支付卡待投递及提现提醒缺失。

最小验证：未读总数大于当前页条数时读一条仍准确；后台产生一条人工/工单回复后铃铛自动变化；从任一入口读后另一入口同步；实际业务事务产通知、重复事件不重复发、失败事务不留下成功消息。

不改变资金、收益、提现审批、安全和顾问分配政策，不改后台管理界面。系统级离线推送需要原生应用标识、厂商推送配置、设备令牌注册及真机权限/点击验收；本轮实现前台提醒和恢复补拉，不将其表述为杀进程后仍能推送。

#### [FEAT-MSG01] 统一入口与服务消息

**① 用户故事**：作为已登录账户，我想从右上角看到通知、顾问/客服回复和工单进展，以便不会因为入口分散而漏掉消息。

**② 验收与异常**：Given 通知、人工和工单各有未读，When 打开任一铃铛，Then 直接进入全屏消息中心，总数为三者合计，一级分为“通知”“服务”，服务内可到达顾问、客服和工单。打开入口本身不标已读。
- 异常1：网络失败时保留上次成功数据，显示失败与重试；不能把失败当零未读，不能显示内部错误码。
- 异常2：账户切换/退出时清掉旧快照，旧请求和计时器不能回写；隐藏 AI 会话不得参与未读汇总。
- 异常3：服务分类关闭新建时，已有历史仍可进入；无历史显示空状态，不伪造顾问和回复。

**③ 数据字典**
| 字段 | 类型 | 默认 | 生成规则 |
| totalUnread | 非负整数 | 0 | notificationUnread + humanUnread + ticketUnread |
| humanUnread | 非负整数 | 0 | 已有 advisor/support 会话未读之和，不含 AI/已移除会话 |
| ticketUnread | 非负整数 | 0 | 已有全部工单 unread 之和，以服务端协议为准 |
| section | notifications/service | notifications | 同一消息中心状态，入口可带初始分区 |

**④ 状态机与禁止动作**：未加载→加载→成功/错误；错误可重试；切账号→清空→新账号加载。禁止因打开总览而清空会话/工单，禁止三种消息互相代写已读。

**⑤ 交互四态**：默认显示两个一级分区、各自未读和对应内容；空状态显示无消息及服务入口；加载态使用已有骨架；报错态保留历史、提供重试，长标题折行/截断，角标上限展示 99+（浮标沿用 9+）。

**⑥ 点击流矩阵**
| 触发 | 目标 | 反馈 |
| 主页面/子页面铃铛 | /pages/me/notifications?section= | 直接显示全屏中心，保留分区；当前已在中心时不重复压栈 |
| 中心返回 | 来源页面；冷启动时 Me | 保留来源与未读状态 |
| 人工服务浮标、客服渠道“在线会话” | /pages/me/notifications?section=service | 统一进入服务分区；浮标仅显示人工未读 |
| 服务内顾问/客服会话 | /pages/support/chat?cid= | 进入现有全屏聊天，复用只读/可回复规则 |
| 服务内会话管理 | /pages/support/messages | 保留新建会话、分类历史和移除列表功能 |
| 服务内工单 | /pages/me/support-tickets，详情用 ?ticket= | 服务端确认后同步已读 |
| 我的消息入口 | /pages/me/notifications | 统一中心及总未读 |

**⑦ 一致性**：已有 conversation/ticket 对象及读确认 API 保持权威；所有入口进入同一全屏中心并复用服务列表和分类规则；旧 /support/messages 作为会话管理页与聊天异常回退仍可用。

#### [FEAT-MSG02] 通知分类、已读与偏好

**① 用户故事**：作为账户持有人，我想区分资金、设备订单、团队、活动奖励、系统安全，并准确知道还有多少条未读，以便优先处理重要事项。

**② 验收与异常**：Given 一页有1条未读而服务端全量为11，When 读该条，Then 总未读变为10；清理已读不减少其他未读；CTA读确认遵守同样规则。充值、提现、支付卡进入资金，未知类型仍在系统可见。
- 异常1：读确认失败保持未读并允许重试；CTA已成功而附属读确认失败时保留真实跳转，不能重复发起资金操作。
- 异常2：分类内当前页没有项目但仍有下一页时，保留加载更多；周期刷新不能丢掉已加载历史或把分页总数算成当前页总数。
- 异常3：系统必收偏好由服务端强制，旧 false 数据归一，读回与界面一致；保留现有六键偏好协议，不把新展示分组写回旧协议。

**③ 数据字典**
| 字段 | 类型 | 规则 |
| kind | 原始字符串 | 保留服务端类型，展示映射不丢失来源 |
| group | finance/device/team/rewards/system | 共用映射，未知归 system；NOVA 业务来源按实际事件类别映射，不恢复 AI |
| priority | critical/high/normal/low | 服务端权威，critical/high 可见重要标识；保留服务端排序/保留期 |
| unread | 整数 | 全量总数；单条成功减1、clearRead不变、allRead成功后重新对账 |
| readAt | 时间戳或空 | 服务端确认后更新；重复读不重复扣 |

**④ 状态机与禁止动作**：unread→read→可清理；批量已读仅作用通知分区。禁止点击“全部已读”顺带清掉未看过的服务回复；禁止静默删除 critical/锁定消息；通知 CTA 仅导航到业务详情，不代替授权操作。

**⑤ 交互四态**：默认分组筛选与重要标识；空状态区分真的无记录与需要继续翻页；加载态禁用重复提交并保留现有内容；报错态保留内容及重试，金额/文本不溢出。全部已读明确写“通知全部已读”。

**⑥ 点击流矩阵**
| 触发 | 目标 | 反馈 |
| 分类筛选 | 当前列表 | 不改服务端偏好 |
| 展开通知 | 本条详情 | 确认读后同步角标 |
| 通知全部已读 | 仅通知 | 成功后对账；失败可重试 |
| 清理已读 | 仅符合既有服务端删除规则的通知 | 保留未读总数 |
| 通知 CTA | 服务端返回的既有路由 | 导航到对应业务页面，禁止猜测资金结果 |
| 偏好设置 | 现有设置页 | 系统必收不可关闭，其余旧开关继续生效 |

**⑦ 一致性**：分类纯函数用于统一全屏消息页；后台模板类型与前台映射对齐，支付类必收与业务详情状态一致。

#### [FEAT-MSG03] 到达、生命周期与消息生产

**① 用户故事**：作为等待业务结果或服务回复的账户，我想在 APP 前台看到新未读，并在回来时补齐遗漏，以便不用反复手动刷新。

**② 验收与异常**：Given 已登录且前台，When 新通知或工单回复到达，Then 一个全局刷新循环最终更新角标（目标15秒内）；人工会话沿用 WebSocket + 断连轮询。恢复前台立即补拉。
- 异常1：断网时不清已有数值，不并发堆积请求；重新联网/回前台重试。退后台/退出账户停止循环，迟到结果不得污染下一会话。
- 异常2：重复到账回调/提现事件只能产生同一业务状态的一条通知；回滚不残留成功通知；无归属/非法对象不投递给猜测的账户。
- 异常3：现有 PENDING 充值/支付卡记录安全补成已投递，不改已读/删除记录；通知失败不得把真实已完成资金状态展示成业务失败。

**③ 数据字典**
| 数据 | 来源与规则 |
| 充值、支付卡 | 既有 nx_notification 业务标识幂等，事务完成后可见 |
| 提现 | submitted/审核状态/转账处理中/成功/退款或取消等真实已有状态；同业务号+状态去重；标题正文 zh/en/vi，CTA真实详情 |
| 人工回复 | 既有 conversation 协议；不复制到 nx_notification |
| 工单回复 | 既有 ticket unread/version；前台统一补拉 |
| 活动/团队/锁仓等 | 已有真实 producer 与已启用模板继续使用；未产生真实业务事件的目录声明不能被声称已覆盖 |

**④ 状态机与禁止动作**：foreground/authenticated→运行；hidden/unauthenticated→停止；恢复→补拉→运行。业务消息 pending→delivered→read；禁止将未成功业务状态改写成到账；不更改提现状态机。

**⑤ 交互四态**：默认静默更新未读与重要标识；空状态不制造欢迎推送；加载态不闪空列表；报错态可重试并保留上次快照。关闭 APP 后的系统推送属于明确未接入能力，不在界面虚假承诺。

**⑥ 点击流矩阵**
| 触发 | 目标 | 反馈 |
| 回前台 | 刷新三种数据 | 保持当前位置/已加载历史 |
| 读人工回复 | 现有会话读确认 | 铃铛与浮标同步 |
| 读工单回复 | 工单版本读确认 | 工单与铃铛同步；新版本仍未读 |
| 到账/提现通知 | 对应资金记录详情 | 可查服务端真实状态 |

**⑦ 一致性**：业务事件、通知记录和资金状态各保留已有事务/权限边界；不引入第二套聊天、消息总线或轮询框架。

## 实施与验收顺序

1. 固定方案与接口；前端数据、前端UI、后端投递按互不冲突文件并行实施。
2. 定向回归：分页总数、重复已读、旧账户迟到回包、前后台启停、工单/人工聚合、五组映射、支付必收、提现重复事件/回滚。
3. 独立审查：资金事件与权限、TS状态竞争、交互/需求完整性；P0/P1回源复现修补。
4. 5180 实景覆盖铃铛/子页铃铛/完整中心/浮标/我的/人工/工单，zh/en/vi 与窄屏，读后刷新、异常重试；保留实测证据，不能以代码声明代替。
5. 同步所属 PRD 功能契约和更新日志；全量 verify 与后端测试；按现有远端分支和质量门提交推送。原生系统推送缺少实配/真机验收时单独列未交付项。
