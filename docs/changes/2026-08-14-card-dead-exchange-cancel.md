# 卡:「撤销兑换单」是条死路径 —— 函数写好了,没人调

**发现方式**:2026-08-14 逐条核 86 条台账欠账时,`/api/exchange/:param/cancel` 一开始被我
判成「产品缺口」(用户能撤销但 PRD 没写)。**回源核到第三层才发现判错了** —— 用户根本点不到。

---

## 事实

`src/pages/me/wallet-exchange.vue`:

- 第 230 行定义 `async function cancelRemoteOrder(exchangeNo)`
- 它里面第 234 行调 `exchangeApi.cancel(...)`,幂等键、失败态、错误码一应俱全
- **全文件搜 `cancel`,只有定义处这一处命中;模板里没有任何绑定**

也就是说:**没有任何东西调用 `cancelRemoteOrder`**。用户在兑换页看不到、也点不到「撤销」。

## 这是什么

与本轮开头删掉的那个卡时代早购镜像**完全同型,只深一层**:

| | 早购镜像(已删) | 本条 |
|---|---|---|
| 接口方法 | 有 | 有 |
| 接口方法的调用者 | **无** | 有(`cancelRemoteOrder`) |
| 再上一层的调用者 | — | **无** |

**所以接口台账门看不见它** —— 那道门问的是「这个地址在代码里有没有被引用」,答案是「有」。
它答不了「这条引用链最终有没有人走」。**静态引用存在 ≠ 可达。**

## ⚠️ 不要顺手把 CANCELLED 展示一起删掉

同文件第 401 行有 `CANCELLED: t.value.exchange.swapCancelledReason` —— 那是**展示**侧,合法且必须留:
服务端仍可能把单据置为已撤销(到期、风控、运营干预),页面要能如实显示。

**死的只是「客户端发起撤销」这一条路**,不是「撤销这个概念」。

## 处理方案(2026-08-14 主人问「最合理的处理」,以下是回源之后的答复)

### 🔴 结论:补上入口,**不要删**。而且这不是「加个功能」,是补一个**已经存在的死胡同的出口**。

先摆三条把结论定死的事实,都是回源核到的:

1. **排队是 PRD 定义过的正经功能**(§9.4.3 `/api/exchange/queue`):用户当日兑换**触顶个人上限**后,
   可以选择把这笔**推到下一个平台日**成交。不是边角料。
2. **页面已经把排队单显示给用户看了**(`displayQueue`,按 `QUEUED` 状态过滤后渲染)。
   用户明确知道「我有一笔在排队」。
3. **但没有任何退出口** —— `cancelRemoteOrder()` 是唯一一条能撤的路,而它零调用。

把三条合起来看,当前产品的真实形态是:

> 用户被锁定在一笔**明天才成交、且明天汇率未知**的兑换上,看得见它,却撤不掉它。

**这才是缺陷本身。** 「撤销」不是锦上添花的功能,是这个状态**唯一的出口**。
删掉 `cancelRemoteOrder` 等于把这个死胡同**焊死并抹掉证据**——门也不会再报,因为端点引用没了。

### 为什么不选「删掉」

与本轮开头删掉的卡时代早购镜像**性质完全不同**,不要因为「同样是零调用」就套同样的处置:

| | 早购镜像(删对了) | 本条(不该删) |
|---|---|---|
| 对应功能在 PRD 里 | ❌ 已被改名删除 | ✅ §9.4.3 明确定义了排队 |
| 用户能否感知该状态 | ❌ 完全不可见 | ✅ 页面就显示着排队单 |
| 删掉的后果 | 清掉一个过期名字 | **把用户的唯一出口焊死** |
| 代码完成度 | 只有接口壳 | 幂等键 / 失败态 / 错误码俱全,像**入口没接上**而非残留 |

### 落地建议(按此顺序)

1. **先补 PRD**:§9.4.3 加一小节写清「排队单可撤销」的规则 —— 可撤的状态范围(仅 `QUEUED`)、
   撤销后额度是否退回当日/次日、是否有次数限制、已进入成交流程后是否还可撤。
   ⚠️ **这几条必须产品定**,代码里看不出来,我不替你定。
2. **再接入口**:兑换页的排队单每行加「撤销」;`cancelRemoteOrder()` 已备好,接上即可。
   撤销是资金相关动作,按本仓规矩要有二次确认 + 失败态 + 撤销后回读服务端状态。
3. **顺带向后端确认一件事**:排队期间用户的资金**有没有被占住/冻结**。
   本仓查不到答案(排队语义在服务端)。若占住了,那「无法撤销」就不只是汇率风险,
   而是**资金被锁且无解锁路径** —— 优先级要往上提。建议并入交接书问。

### 在此之前

保持现状(函数留着、入口不接)。**不要**因为「它是死代码」就顺手删 ——
留着它是留着修复的材料;删了下次还得重写,而且死胡同会变得不可见。
