# 卡:余额到底谁说了算 —— 服务端周期覆写 vs 客户端本地扣款

- **状态**:🅿 待规格(主人 2026-08-13 拍板立卡)
- **来源**:z6 扣款自愈包的 R1 独立审计旁证出来的结构性问题,已超出那张卡的范围。
- **优先级理由**:它是**前置**。z6 想修的「扣款报假后没有自愈」以及任何后续「修余额一致性」的卡,
  在这个问题定论之前都无法正确设计 —— z6 已经实证:照现状设计出来的方案是净负面的。

## 1. 现象:同一个数有两个写入者,互不知情

| 写入者 | 何时写 | 写什么 |
|---|---|---|
| **服务端投影** `refreshRemoteFleet`(`store/app.ts:700-723`) | `remoteApiEnabled && !fundsSandboxEnabled` 时,每次刷新(启动 / 前台 / 业务页多处 / tick 节流) | `usdtBalance = fleet.walletUsdt`,并用它**重算** `earningBuckets` |
| **客户端本地扣款腿**(z5 引入,`applyWithdrawalDebit` / `refundWithdrawalDebit`) | 提现建单成功后 / 失败终态退款时 | 本地增减 `usdtBalance`,并 clamp `withdrawableUsdt` |

两者**对同一个字段各写各的**,没有任何一方知道对方存在。

档位判定(`api/runtime-config.ts`):生产无 env → `remote`;开发无 env → `sandbox` 但 `modeExplicit=false`
⇒ **这两档 `fundsSandboxEnabled` 都是 false** —— 服务端投影与本地扣款**同时生效**。

## 2. 已经造成的后果(全部回源坐实)

1. **本地扣款的效果不确定**:服务端值若已含这笔扣除 ⇒ 本地再扣就是**双扣**;若不含 ⇒ 本地扣的 −N
   会被下一次投影**抹掉**,而幂等键已置位 ⇒ **永不重试**。
2. **可提桶有三个交替写入者**:扣款 `min()` 夹小(有损)· 退款腿明写**不回补** · 投影整体重算。
   ⇒ 提现页的可提上限随刷新抖动。
3. **一句错注释污染了后续所有修法**:`applyWithdrawalDebit` 头注称
   「全仓没有余额端点,余额的唯一持有者就是本 store」—— **这句是错的**,而 z6 整包就建立在它上面,
   做到全绿才被独立审计推翻。**注释不参与编译,过期了没人知道。**

## 3. 要拍板的是什么(不是实现细节,是权威归属)

- **谁是权威?** 三选一,不同选择推出完全不同的实现:
  - **服务端权威** ⇒ 本地扣款腿(z5 的两个函数)应当**删除**,提现后的余额变化等投影;
    代价:投影有节流与静默失败,余额更新会有可见延迟,且离线不可用。
  - **本地权威** ⇒ 投影里的余额覆写应当**停掉**,改由本地账本推导;代价:与服务端真值可能长期背离。
  - **分档** ⇒ 例如 mock 走本地、remote/sandbox 走服务端;代价:两套语义并存,每个消费者都要问「现在哪档」。
- **可提桶谁算?** 它现在既被本地 clamp、又被投影重算,必须指定**单一写入者**,其余只读。
- **过渡怎么走?** z5 的扣款腿已经合并且在跑,拆除或停用需要一次可回滚的迁移。

## 4. 机器门方向(定论后焊)

- 禁止「余额字段有第二个写入者」:扫 `usdtBalance` / `withdrawableUsdt` 的所有赋值点,
  白名单之外一律判红(判据取磁盘真实赋值点,不手写清单)。
- 禁止注释宣称「没有 X 端点」而实际存在:把这类立论前提做成可机器核对的断言
  (例:注释里点名的端点缺席才允许写「没有」)。
