# 结构性反思 · 包 z7 —— 「判据没命中被测对象」在一个包内出现三次

> 触发:`nexion-audit` 铁律「同型错误 ≥2 轮出现 → 强制结构性反思,产出书面结论才许继续」。
> 本包内同族三次,已达触发线。**本文写完之前不许再对这一族打补丁。**

## 同族三个实例(都是「门看起来在测,实际没测到」)

| # | 实例 | 谁发现的 | 表现 |
|---|---|---|---|
| 1 | runtime 门 ⑧ 的靶从未先落盘 → 三路合并的冲突分支一次都没执行 | R1 独立审计 | 被测行为坏成什么样都绿 |
| 2 | 网络桩不看请求单号,一律回同一份报文 → 本轮结论被套到其它在途单上 | 我自己(因为断言时红时绿才发现) | 时绿时红;绿的时候不知道是真绿还是刚好没撞上 |
| 3 | 「再提一笔」控件标签在门里**手抄**成 `submit another`,真值是 `Withdraw again` | 我自己(断言报「找到 0 个控件」) | 判据零命中 —— 差一点被当成通过 |

## 四问

### ① 拆到不可再拆的事实:什么结构让它必然发生

不是「我不小心」。三个实例的共同形状是:

> **断言只检查「结果」,不检查「起点是否真的成立」。**

`期望 Y 在 X 之后发生` 这种断言,当 X 从未发生时**恒为真或恒为假**,而两种都不报「X 没发生」。
门里没有任何东西强制「先证明被测场景真的被构造出来了」——构造与断言之间是断的。
实例 3 是同一件事的另一面:判据里写的**字面量**没有任何东西保证它对应磁盘上真实存在的东西。

### ② 为什么第一次的修法没挡住第二次

R1 给 ⑧ 的修法是**在那一格加一行 `persistAccountSnapshot()`** —— 症状层。
它修好了那一格,但没有产生任何约束让**其余每一格**也去证明自己的起点。
于是同一形状在同一个文件里换个位置又出现了两次(桩不认单号、标签手抄)。
**修错层了**:该修的是「门怎么写」,不是「这一格怎么写」。

### ③ 同族还有几个没被发现 —— 逐格扫

对 `withdraw-status-mirror-runtime.mjs` 每一格问同一个问题:**它证明自己的起点了吗?**

| 格 | 起点是什么 | 现在证了吗 | 处置 |
|---|---|---|---|
| ① 被调用 | 单据在在途集里 | ✅ `seen` 里有对该单号的 GET,本身即证 | 保持 |
| ② confirmed | 起点是 processing | ❌ 没证 | 补前置断言 |
| ③ 落盘 | 同上 | ❌ | 随 ② 一起 |
| ④ TX_ORPHANED | 起点是 processing 且**盘上没有冲突行** | ❌ 没证,且「无冲突」是隐含前提 | 补前置断言 + 写明它不测合并 |
| ⑤ 原因归一 | 起点是 processing | ❌ | 补 |
| ⑥ retriable | 同 ⑤ | ❌ | 补 |
| ⑦ 解析器 | 无起点(直接喂报文) | — | 保持 |
| ⑧ 同状态改字段 | 靶**必须**先落盘 | ✅ R1 后已补 | 保持 |
| ⑨ 接线 | 业务循环真的在跑 | ⚠️ 只证了「被问了」,没证「循环起得来」 | 记为已知限制(R1 critic 亦提到) |
| ⑩ frozen 出边 | 靶必须先落盘 | ⚠️ 落了盘但没断言落成功 | 补前置断言 |
| 渲染面 | 靶单据可被页面读到 | ❌ | 补 |

**结论:11 格里 6 格没有起点证明。** 这不是三个孤立失误,是一整族。

### ④ 能不能一条不变量或一道机器门根治

能,且必须是**写法上的不变量**而不是「记得检查」:

> 🔴 **每个场景先落一格「起点断言」,再落结果断言。起点断言不过,结果断言的绿一律不作数。**

落地方式(R2 审计解冻后实施):
1. 门里所有场景改走同一个 `scenario(id, setup)` 构造器,它**返回被观测到的起点**,
   并强制调用方先 `check("起点成立", ...)`;
2. 门里**禁止手写**任何来自产品代码的字面量(控件标签 / 文案 / 单号前缀),
   一律从源码或 i18n 读真值,读不到即抛(实例 3 的根治);
3. 网络桩一律**按请求参数应答**,不匹配即抛(实例 2 的根治,已实施)。

**为什么这是更强的层**:1 与 2 让「忘了证起点」和「手抄字面量」变成**写不出来**,
而不是「写出来了希望有人发现」。上一次的修法停在「这一格补一行」,这一次停在「门只能这么写」。

## 判据自查

- 有没有出现「下次注意 / 记得检查」?**没有**;三条落地项都是构造性的。
- 落盘了吗?**本文件**;实施后在变更提案与 `docs/PORT-PITFALLS.md` 各留一行指针。

## 落地情况(2026-08-11 R2 后)

- ✅ **起点断言已实施**:`seed()` 现在返回被观测到的起点(在内存 / 在在途集 / 在盘上),
  门里新增 `⓪` 一格统一断言。**它当场就红了一次** —— 抓到我把判据写得太粗:
  渲染那格的靶**故意是终态单**(终态本就不在在途集),一刀切会把「靶摆对了」误判成失败。
  据此改成按场景定义起点(回读类必在在途集 / 渲染类必已落盘)。**判据本身也要经得起这一问**。
- ✅ **禁手抄字面量**:控件标签改为从 i18n 源码读真值,读不到即抛。
- ✅ **桩按请求参数应答**:不是目标单号就抛。

# 第二族(R2 触发)—— 「替身判据只修了一个方向」

> 触发:同一个 `mergeWithdrawals` 的同一族缺陷,在 R1 修完之后,R2 又抓到两条。
> 同族第二次 = 结构在说话,先落笔再动手。

## 事实

R1 我把判据从 `c > a` 改成 `c > a || (c === a && ct > at)`。探针实跑(磁盘 frozen t=100,内存新结论 t=200):

```
frozen → processing   => frozen   ❌
frozen → sent         => frozen   ❌
frozen → confirmed    => frozen   ❌
frozen → refunded     => refunded ✅
frozen → tx-failed    => tx-failed ✅
反向:磁盘 confirmed(t=200) vs 内存陈旧 frozen(t=100) => frozen ❌
```

**坏结局走得通,好结局走不通**:冻结单被后台核查通过、放行回主链的每一次,都被静默丢弃。

## 四问

**① 最小成因**:我把 `mirroredAt` 当成**档位制度内部的平局裁决**,而不是**取代档位**。
档位仍是主判据,于是只有「档位打平」这一条路径能用上真实时序;
「档位说反了」(frozen 排在 processing 之上,而 frozen→processing 是真实的正向流转)那两条路径原样保留缺陷。

**② 为什么上次的修法没挡住这次**:上次修在**同一层**——我在既有判据后面加了一个 `||` 分支,
没有质疑判据的**主干**。R1 的反思写的是「门没测到起点」,是**验证层**的反思;
判据主干选错这件事属于**设计层**,上一轮完全没碰。修错层 = 同族必然复发。

**③ 同族还有几个**:把「用替身判据决定谁赢」抽象成族,本文件所在仓内至少还有:
`WITHDRAWAL_STATUS_RANK` 这张表本身(frozen 排 6 就是一次「用严重度冒充时序」),
以及 `TIME_ANCHOR_KEYS` / `ADDITIVE_NUMBER_KEYS` 两套按字段名分类的合并规则(同样是替身)。
本包只动提现单这一支,另两支超范围 —— **但必须写下来**,否则「只修被点那处」又会重演。

**④ 一条不变量根治**:

> 🔴 **有真信号时,替身一律不参与裁决。**
> 具体到这里:任一侧被镜像过(有 `mirroredAt`)→ **纯按镜像时刻裁决,完全不看档位**;
> 两侧都没被镜像过(mock 档 / 存量单)→ 才回落到档位。

这比「加一个平局分支」强在:它把档位从**主判据**降成**兜底**,
于是「档位排序是否正确」不再能影响任何一条被服务端驱动的流转 ——
frozen 排第几都不再有后果。机器门同步补 rank 不等的两个方向(R2 也点名了这条门缺口)。

## 判据自查

- 修法落在比上次更强的层?**是** —— 上次改的是判据的一个分支,这次改的是**谁当主判据**。
- 出现「下次注意」了吗?**没有**。
- 同族其余两支已列名并标记超范围,不假装不存在。
