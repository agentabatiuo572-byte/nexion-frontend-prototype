## 3. 🔴 新发现(不属于原 AC,只报不修):并发建单后**钱没扣**

### 现象

两个标签页同刻提交,**只建出 1 单(AC 满足)**,但那一单的**扣款没有落盘**:

```
干净 raw 实测(不初始化任何 store,直接读 localStorage):
round 2  winner=B  建单数=1  单号 WD-20260731-2702
         raw 余额  24856.56 → 24856.56   扣了 0 次
         raw 最终单号  null                ← 落盘快照里根本没有这一单
         raw 计数  {dayIndex:20665, count:1}
```

主 12 轮里同一现象的另一面(新开标签页 = 用户下次打开看到的):

```
round 7  B 建单 WD-20260731-9924
         余额起 24856.56 → 落盘 24856.56  (扣了 0 次)
         提现账单条数 1 → 2               ← 账单里有这笔提现
         落盘最新单号 null
```

**即:用户提了 25 USDT,提现单和账单流水都在,但余额一分没少。** 这正是本工程别处已明确设防的那一类(`submitWithdrawal` 注释里的 "infinite-mint vector" / 「并发透支门 2026-07-31 审计 P0」)。

主 12 轮那份用的是「新开页 + store 读」,受我自己前面 `readAll` 的回写干扰,数出来是 3/12;**以上面 18 轮 raw 直读为准**。

### 排除项(墨菲:先把「是我测错了」逐个证伪)

| 怀疑 | 对照实验 | 结果 |

### 机制(`[INFERRED]` MED 置信度 —— 我没做到完全定位,只报不修)

两个标签页各自持有整份 `user` 快照并会各自整体落盘;胜者写入「已扣款」的那一份之后,**败者页在某个时点又把自己那份「未扣款」的整份快照写了回去**,后写覆盖先写。证据侧写:动作轨迹显示两页都有约每 3 秒一次的 `creditNex`(NEX 计息 tick),每次都会带着**整个 `user` 对象**落盘。

`[GUESS]` 这套「整份快照 last-write-wins」大概率是既有的 account-cloud 语义,不是本次改动引入的;但**本次改动让它第一次被踩到** —— 改之前两页都建单成功、不存在「败者」,也就没有败者那份未扣款快照去覆盖。我没有测过改动前的版本,这一句是推断不是实测。
