## 四问

### ① 根本路线选错没?

**没有。** 两轮 15 个独立 agent,**没有一个质疑过产品路线**(计数从单据列表现算、上限取服务端)。
R2 的 P0 全部落在「实现与验证」这一层,且集中在我自己 R1 的补丁上。
主人拍板 A 之后,与已签字规格的唯一实质偏离(并发仲裁交给服务端)也已获授权 —— 路线成立。

### ② 是不是结构导致同型必然复发?

**是,而且是两条独立的结构。**

**结构一:我验证「正常路径」,不验证「失败路径」。**
族 A 三条全部是失败/异常路径的断言(落盘失败、跨标签页、刷新)。正常路径我会跑浏览器、会写固定靶;
失败路径我**只写注释**。而注释不参与执行 —— 它写什么都不会红。
这与本包修的原始缺陷同构:**声明存在、执行缺席**。

**结构二:我用「声明的数量」冒充「实际的覆盖」。**
族 B 六条的共同点:PASS 行上的数字(20000 组、3000 轮、样本量 5)是**循环上界或手写常量**,
不是**实测的有效样本数**。而随机域的上界又是我自己设的 —— 于是「域外的破坏」天然测不到,
且我永远不会知道,因为报告只告诉我跑了多少轮,不告诉我覆盖了多少种。

### ③ 同型族的共同根因 → 一条根治,禁止逐个打补丁

| 族 | 一条根治 | 禁止的做法 |
|---|---|---|
| **A** | **失败路径必须有注入测试才允许写行为注释**。本包涉及的失败注入建成一个套件(落盘写失败 / 网络超时 / policy 非法 / 存储配额满),并登记进 verify —— 仓内已有 `run-contract-suite` 登记门的先例(未登记即红) | 给每条错注释单独改文字 |
| **B** | **报出去的数字必须是实测的,不是声明的**:① 随机发生器换成不溢出的(`Math.imul`);② PASS 行打**实测 distinct 指纹数**并对它设下限;③ 随机域上界必须**超出实现里任何常量的取值范围**,并显式塞一轮远超上界的极值 | 把域上界从 50 调到 60(下一个 61 照样漏) |
| **C** | **照抄现成写法时,抄的是「那处的全部约束」而不是那几行**:动手前先列出同族现存实现的约束清单(守卫 / 生命周期钩子 / 清理),逐条对照 | 逐条补漏掉的那个钩子 |

### ④ 层级归位

| 层 | 落点 |
|---|---|
| 能机器测 | B 全部三条焊进哨兵;A 的注入套件登记进 verify;C 的「定时器必须 onShow/onHide 成对」可扫 |
| 需判断 | 「这条注释断言的行为,我执行过吗?」→ 进 `nexion-audit` 修复阶段自查清单 |
| 跨任务心智 | 「**失败路径的注释是零成本谎言**」+「**声明的样本量不是覆盖率**」→ memory |

## 结论

**不是方向性错误,是执行层的两条结构性错误**,且 R1 的反思只修了其中半条。
按铁律「确有结构问题 → 先改结构再继续」:本轮先落 ③ 表里的三条根治,再回头收 R2 的其余条目。
