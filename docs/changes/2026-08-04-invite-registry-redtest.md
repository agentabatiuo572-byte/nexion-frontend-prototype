# 创世邀请码:码表核销(FEAT-GEN11)· 红测留痕

**日期** 2026-08-04 · **门** `scripts/selfcheck-genesis-invite.mjs`(已焊进 `scripts/verify.sh`)

## 修的是什么

`app.ts` 的 `setGenesisInviteCode` 原本只跑一条正则 `/^NEXGRID-OG-[A-Z0-9]{4}$/`:

- 任何符合格式的串都通过 —— **从未发放过的码照样能用**;
- 同一个码可被**无限个账号**核销,一码一用形同虚设;
- 资格门 `use-genesis-eligibility.ts` 的 `hasInvite` 只看字段非空,等于只看格式。

改为查平台码表(`src/store/genesis-invite.ts`)+ 三态校验:码不存在 / 已被使用 / 已作废 /
本账号已持码,四种拒绝各自归因、各自文案(三语),资格门改判「本账号真持有一个已核销的码」。

**码表权威源 = 运营后台的发码 / 作废功能,落点 2026-08-04 待主人裁决**;前端侧用出厂 seed
提供「运营已发过的一批码」,不依赖后台即可独立成立。后台落点定了以后只换 `readRegistry`
的数据来源,其余逻辑与全部调用方一行不用改。

## 并发的残余窗口(如实声明)

`claimGenesisInviteCode` 走「先占后改 + 单次落盘」:前置条件在**当下从磁盘读到的最新码表**
上复核,不用任何内存副本 —— 所以「另一个账号刚核销掉这个码」这一格拦得住。

🔴 但 localStorage 没有锁,「读表比状态」与「写回」终究是两步。同源多标签页恰好卡在这两步
之间同时提交,理论上仍可能双方都通过判定(亚毫秒级)。客户端消不掉这一格(Web Locks 只有
H5 有,uni 多端不可用)。真后台由 server 单事务(唯一约束 / SELECT … FOR UPDATE)保证,
本机制随 mock 一起退役。

## 红测方法

- 只用 `cp` 备份 / 还原,**绝不 `git checkout`**(仓里有并发 agent,checkout 会抹掉别人未提交的活)。
- 每次注入后先证实**注入真的落盘生效**(文本确实变了),否则直接抛错终止 —— 空转的红测比没有
  红测更糟,它会给人「验过了」的错觉。
- **按合取项逐个隔离**:一次只破坏一个判据,看对应断言是否真的红。
- 还原后按 sha256 核对 **byte-identical**,并复跑到全绿。
- 驱动脚本 `redtest.mjs` 与逐条结果 `redtest-results.json` 在本轮 scratchpad(`impl-invite/`)。

## 「本账号已持码」为什么问码表、不问 `user.genesisInviteCode`

两个坑,都是先写成「问内存字段」才发现的:

1. **陈旧标签页**:同一个账号开两个标签页,A 核销完 B 的内存副本仍是「没持码」——照它放行,
   同一个账号就能在两个标签页各占一个码(⑩ 固定靶)。
2. **存量账号**:旧实现只校验格式,历史上写进 `user.genesisInviteCode` 的串码表里根本没有。
   照字段判「已持码」,这批人**既不算持码(资格门不认)、又不许再核销**,被卡死在死角(⑦ 固定靶)。

改法:`redeemedInviteCodeOf(accountKey)` 问码表(每次现读磁盘),资格门与「已持码」判定共用它 ——
一个单源,两处口径永不打架。`user.genesisInviteCode` 仍写、仍是 per-account 凭证展示字段,
但不再是判定依据。
