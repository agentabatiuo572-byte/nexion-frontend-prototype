## 🔴 证伪结论(最上面,先看这段)

**致命的那条(已回源坐实,不是 agent 的一面之词)**:

> 「由收据咽喉合成一次写入」这个前提**不成立**。四个资金原语
> (`creditBalance` / `debitBalance` / `creditNex` / `debitNex`,`app.ts:912/927/950/965`)
> **每一个内部都自己调 `persistAccountSnapshot()`**,而账单是在这些之后才 `addMany`
> (`money-receipt.ts:149-155` 逐腿调原语 → `:166` 才追加账单)。
> **钱先落一次盘、账单再落一次,要修的那个窗口原样还在。**

想补救就得再加「原语不落盘」模式,而那条路上等着 **P0-2**:
`addMoneyApplied` 只在落盘成功后记账(`app.ts:1014`),deferred 下差值恒 0
→ `restoreMoney` 判「一分没动」直接 `return true`(`app.ts:1051`),**而内存里钱已经扣了**;
随后每秒一次的 tick persist 把这笔少的钱写进磁盘。**回滚报成功,钱真没了。**

其余 P0(逐条附了文件行号与实跑用例):
- **P0-3 换号时序**:`app.bindAccount` 末尾就 persist(`app.ts:434`),而 `bills.bindAccount`
  要等 `rebindAccountScopedStores` 才跑 → **上个账号的账单被写进新账号的行**(实跑坐实);
- **P0-4 存量迁移**:`bills.ts:122-131` 读不到就 `seedBills()` → 快照里没有 `bills` 字段的
  **全部存量用户**,首次加载即被静默替换成一份假历史(30 天流水 + $50 充值),页面看着完全正常;
- **P0-5 `addForAccount`**:从「覆盖别人的账单行」退化成「**覆盖别人的整个资金行**」——
  三路合并的基准是当前账号的,对目标账号不可用,`wallet-withdraw.vue:1001/1011` 连写两次 = 两次整行覆盖;
- **P0-6 我以为的安全网兜不住**:`selfcheck-snapshot-literals.mjs` 只判**字段集相同**,不判**怎么合**。
  实跑:最省事的写法三处字段集一致(门必绿),两个标签页各追一笔后**只剩一笔**。
  「literals 门会兜住新字段」这句前提错——它兜的是「字段在不在」,不是「合得对不对」。

**我写进提案的前提被推翻了三条**:①「不搬内存归属也能一次写」(P0-1)②「literals 门兜得住」(P0-6)
③「P-031 禁止 store 互 import」(`rewards-seen.ts:4` 早就 import 了 `useBills`,已有例外)。

## 一、要解决的那件事

一次资金变动现在写**两次盘、两个 key**:

| 顺序 | 谁写 | 写到哪 | 并发方案 |
|---|---|---|---|
| 1 | `app.persistAccountSnapshot()` | `nexgrid-account-cloud-v1` | 三路增量合并 |
| 2 | `bills.persist()` → `writeAccountRow` | `nexgrid-bills-accounts-v1` | 裸读写(LWW) |

两次之间没有事务。进程在中间没了(切后台被回收 / 关标签页 / 刷新),就落下**钱变了但没凭证**或**有凭证但钱没变**。
`uni.setStorageSync` 是单 key 的,**只要还是两个 key,就不可能原子**——这是物理约束,不是实现没写好。

## 二、提案(相对 v2 §三收窄,不搬内存归属)

设计 v2 原写的是「把账单内存归属搬进 `app.ts`,`useBills` 降级成门面」。回源读 `bills.ts` 后我改判:**那一步不必做**,而且它会踩 P-031(store 之间不互相 import)。

改成三小步:

1. **账单数组仍归 `useBills`**,11 个消费者一行不改;
2. **删掉 `bills.persist()` 的独立写盘**——账单不再自己碰磁盘;
3. **快照里带上 `bills` 字段**,由 `src/lib/money-receipt.ts` 里那个**已经存在、已经被机器门焊死的收据咽喉**合成一次写入:
   在内存里改完钱、追加完账单,再调**一次** `persistAccountSnapshot`。

`money-receipt.ts` 本来就同时 `useApp()` 和 `useBills()`,它在 lib 层不在 store 层 —— 这条路径不新增任何 store 互相 import。

**为什么由它合成**:全站资金路径已被 `selfcheck-money-receipt.mjs` 强制收敛到这个咽喉(白名单只剩 3 处例外)。
把事务边界放在咽喉上,等于**复用已有的那道门**来保证「没有绕过事务的资金写入」,不必再造一道新门。

**配套已就位**:`selfcheck-snapshot-literals.mjs`(commit `e02d50a`)守着「快照三处字面量字段集必须一致」。
`bills` 是新字段,三处漏一处就会被它当场判红 —— 这正是先焊它再动的原因。

## 二·补 — 顺带清掉的死字段(证伪 agent P2-11,已回源坐实)

**但我建议不做这个重构**,依据三条:

1. **省事版做不到,完整版代价极大。** 完整版要一次性动:账单归属搬家 + 事务边界 +
   存量迁移 + 跨账号写法重做 + 状态阶梯 + 数组按 identity 合并 + adopt 回内存 + 5 个 harness 改口。
   **每一处都在资金路径上**,而这是一个 mock 前端——存储层将来整个换成真后端,真后端自带事务。
2. **我在这块的实际战绩是 0 胜 2 负。** 本会话两次改这个存储层,两次都改坏了:
   自愈对账**重复付款**(浏览器实测 11940 → 11943);脏检查**净亏 18.8×**并且

### 🔴 P2-4 那条错报的教训(值得单记)

agent 报「`bills.seed()` 全仓零调用点,死代码」。**我第一次自查也得出同样结论** ——
因为我跑的是 `grep -rn "seed()" src/ | grep -i bill`:**只搜了 `src/`,而且用「行里有没有 bill 字样」筛**。
真正的消费者在 `scripts/selfcheck-withdraw-freeze.mjs:212`,那行长这样:

```js
const store = useBills();
store.seed();          // ← 既不在 src/,行里也没有 "bill" 这个词
```

**两个筛选条件各自把它漏掉一次。** 按这条报告删下去,会当场打断一道机器门的固定靶,
而且 verify 要跑到那道门才报错——中间所有环节都是绿的。

**判据**:凡是要**删**东西,消费面必须包含 `scripts/`(机器门 / harness 也是消费者),
且筛选词只用**符号本身**,不叠加「行里应该还有什么词」这种二次条件
(同族:[[feedback_sentinel_green_without_checking]] 的缩集陷阱、
[[feedback_css_block_deletion_selector_sweep]] 的逐 selector 反查)。
