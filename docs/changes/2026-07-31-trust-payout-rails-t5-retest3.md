## 3. 机制定位(给实现方,只报不修)

拦 `localStorage.setItem` 记录**每一次**对 `nexgrid-account-cloud-v1` 的写入(`$onAction` 拦不到 —— setup store 内部闭包调用不走 action 代理,这是我第一版探针的假阴,已修)。10 轮里 8 OK / 2 少扣,失败轮轨迹:

**轮 1(少扣)**——`t=0` 是胜者 `submitWithdrawal` 的调用时刻,B 是胜者:

```
B@154ms  bal=24831.56  单在     ← 胜者第一次落盘:正确
A@155ms  bal=24856.56  无单     ← 败者 1ms 后整份覆盖:钱和单一起被抹掉
B@297ms  bal=24856.56  无单     ← 🔴 胜者的「+150ms 按单号回读补写」写回的是**旧值**
B@301ms  bal=24856.56  无单
...(此后两页每秒的 tick 一路把旧值写下去,再没变过)
```

**轮 3(少扣)**——更直接,胜者自己把自己写对的那份改回旧值:

```
A@155ms  bal=24856.56  无单
B@156ms  bal=24831.56  单在     ← 胜者落盘:正确
B@282ms  bal=24856.56  无单     ← 🔴 胜者的补写把已经正确的落盘改回了旧值
```

**对照:轮 2(正确)** —— 同样被 1ms 内覆盖,但补写这次把值救回来了:

```
B@164ms  bal=24831.56  单在
A@164ms  bal=24856.56  无单     ← 同样的覆盖
B@315ms  bal=24831.56  单在     ← 补写救回
```

`[INFERRED]` 置信度 MED-HIGH:补写这一步**存在但不可靠** —— 同样的 1ms 覆盖,有时救回、有时写回旧值、甚至能把已经正确的落盘改坏。它是「先合并再整份写」的一次普通写入,而不是一次幂等的定点修复,所以它自己也参与同一场覆盖竞赛。`[GUESS]` 低置信度:与账户快照按字段做三路差分、且写完会把本地基线前移有关(基线前移后,再写时「本次改动量」已归零,合并结果就等于当时读到的那份旧值)。这一句是推断,我没有单独做实验证明,请实现方回源核对。

**结论不依赖上面这段推断**:第 1 节的 40 轮落盘实测就足以判 FAIL。

## 6. Harness 自证伪记录

按纪律留档,以下都是**我的探针问题,不是被测缺陷**:

1. **落盘账单一开始恒读 0**。我把 `nexgrid-bills-accounts-v1` 的形状写成了 `{[acct]:{items:[]}}`,真实是 `{[acct]:{bills:[]}}` → 数组取空、条数恒 0。批次 1 因此改用 store 读,又踩到「store 读的是本页内存,B 页赢时 A 页看不到」。批次 2 修正 raw 形状后才是权威落盘条数。
2. **`$onAction` 拦不到 `persistAccountSnapshot`**。setup store 内部闭包调用不走 action 代理,第一版诊断轨迹全空(`persist次数:0`)。改成拦 `Storage.prototype.setItem` 才拿到真实写入序列。
3. **背景负载会稀释复现率**。批次 2 前半段与坏数据批次并行跑时连续 7 轮全对;**批次 1 是独占跑的**,复现率以它为准(4/20),批次 2 只作补充样本与永久性判定。

沿用并复现的环境事实:必须用 `localhost` 不能用 `127.0.0.1`;`page.goto` 只改 hash 不重载页面(每次 boot 带不同 query);注入 uni storage 要 `{type:'object',data:X}` 包装;uni 产物是 `<uni-text>`;`submitWithdrawal` 是 async 必须 await;toast 会自动消失、要 50ms 轮询 `ui.toasts` 累积。
