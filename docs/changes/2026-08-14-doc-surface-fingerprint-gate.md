## 问题

`docs/业务流程说明.md` §1 整节把「绑卡 → 到期自动扣款」写成当前流程,**11 天没有任何门响** ——

照那份文档实现,会实现出 FEAT-TRIAL02 **明令禁止**的产品。

## 判据:不能简单地「文档里出现即红」

那会把**正确的**文档判红:讲清「这些动作已删除、别照做」、列出门的禁用名单,
都必须原样写出那些名字 —— 本仓三份变更卡和重写后的 §1 都是这样。

所以分两层:

| 范围 | 规则 |
|---|---|
| `docs/changes/**` | **结构性豁免** —— 那里每份都是有日期的变更记录,按定义就是历史 |
| 其余 `docs/**` | 要么**零命中**,要么在文件里显式写一行 `STALE-TERMS-OK: <理由>` |

标记是**有意为之且留了字**的动作,不会手滑加上;**带标记的文件数打进 PASS 行**,不许静默增长。

⚠️ **已知残余风险**(写在门的注释里,不假装没有):带了标记的文件仍可能自己烂掉。
这道门挡的是「**无声地**把死流程写成活的」,不是「所有文档永远正确」。别把它当成后者。

### 正控:防这道门自己假绿

本门 PASS 的形态是「0 命中」—— 那正是假绿最爱的形状:grep 一坏(路径写错 / 通配符失效 /
docs 被挪走),同样 0 命中、同样报绿。所以加一条**必须扫得到**的对照:
`docs/changes/` 里的变更卡按定义会原样引用这些旧动作名。**那里扫不到 = 扫描机制坏了**,当场判红。

### PORT-LEDGER 的两处:门第一次跑就揪出来的真货

1. **架构描述过期**:「trial 早购 = `redeemEarly` 门 → `app.debit/credit/creditNex/addDevice/activateDevice`」
   —— 把已删除的动作写成当前的跨 store 编排方式。现改为 `freeTrial.convert()` 门,
   并写明编排在**结算页**、用户显式确认后执行、设备走订单履约管线不直插。
2. **store 接口清单过期**:「free-trial(全 helper …/canStart/`startWithCard`/`redeemEarly`)」
   —— 列的是已删除的两个动作。已按回源读到的真实现改成 `canStart/start/convert/cancel`。

**这两处正是这道门存在的理由**:它们和 §1 一样,是「文档把死掉的东西写成活的」,
而且藏在一份没人会主动重读的台账里。
