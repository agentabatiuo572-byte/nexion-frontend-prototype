## 修法:一个共用提交器,六个 store 全路径走它

`account-scoped-storage.ts` 新增 `createAccountRowCommit({ tableKey, parse, snapshot, sync })`,
返回 `{ bind, commit, accountKey }`。`commit(apply)` 就是质押那个 `commit()` 的共用引擎:

1. 基准取**磁盘最新**行,不是本标签页可能已经陈旧几小时的内存副本;
2. `apply` 在新鲜状态上**重新校验前置条件** —— 别处已经领走 / 推进过的返回 `null`,调用方拿到
   `ok:false`,绝不会第二次入账(这是双花的根);
3. 带 `rev` 做 CAS 落盘;`rev` 被推进过说明 1→3 之间又被插了一脚,重跑一轮(有界 3 次)。

失败仍分两类:`conflict:true` = 期间被别处改过(页面弹「刚在别处更新过」),
`conflict:false` = 本来就不该成交(不存在 / 已领 / 未到期,既有语义原样保留)。

**为什么抽成共用件而不是每个 store 抄一份**:重试上界、conflict 归因、「失败也要把磁盘最新态
刷进内存」这三条都是**错了不会报错、只会静默双花**的细节;抄 6 份 = 6 个各自长歪的机会。

**`staking.ts` 本轮一个字没动**:它的机器门 ⑥ 按行文 pin 了 `readSnapshot(boundKey)` 等实现
细节,重构它等于同轮改判据;且当时它正被并发会话改着。代价是它保留自己那份内联 `commit()`
(一份重复),换来不动别人在飞的工作 + 不自改判据。已在共用件注释里写明。

### 顺带修掉三个被本修复放大的隐患

- **入账顺序**:`settleCredited` / `settleBankIntent` 原先是「先 `recordDeposit` 动钱、再 patch
  状态」。两端各拿陈旧内存副本判状态门 → 两次入账都过。现在统一「先把状态 CAS 落盘,过了才
  动钱」(与 `submitCardPayment` 既有铁律同形);动钱失败则把单据回滚,宁可「无单无钱」也不留
  「有单无钱」。
- **`settleBankIntent` 原先没有任何状态门**(全靠三个调用方各自把关自己那条边),补了
  `credited` 终态门 —— 这是银行轨双花的闸。
- **单号铸造**:`mintDepositId` 原先只对**内存**账本查重。CAS 之前撞号被 last-write-wins 掩盖
  (其中一笔本来就会被顶掉),现在两笔都留得住,撞号就成真事故(`depositId` 是三轨共享主键,
  `find()` 永远命中第一笔)。改成对**入参那份磁盘最新账本**查重 —— 与质押 `stk-${Date.now()}`
  那条同型。

### 对外签名

`conflict` 一律是**新增可选字段**。原本就返回对象的(`signIn`)直接加;原本返回 `boolean` 的
四个(`voucher.claim` / `dailyPowerUp.claim` / `useSaver` / `claimMilestone`)、返回
`string|null` 的 `luckySpin.spin`、返回 `boolean` 的 `cancelBankIntent` 改成
`{ ok, …, conflict? }` —— 否则页面无从分辨「已在别处处理」与「点了没反应」。

🔴 **这一改带一个陷阱**:返回对象后 `if (store.claim(x))` **恒真**。六处调用点全部改成读 `.ok`,
并由机器门 ⑥ 逐处 pin(见下面 R13)。其中 `daily.vue` 的 `claimMilestone` 原本就**丢弃返回值**
后无条件发奖 —— 本轮修掉,否则接了闸也照样白发。

### 🔴 诚实边界(与一期同口径)

localStorage 没有锁,「比 rev」与「写回」终究是两步,亚毫秒级插队窗口**无法在客户端消除**。
本机制根治的是真正会发生的那个窗口 ——「状态永久陈旧」;残余窗口靠真后端单事务。

`withdraw-daily-count.ts` 是**两道互补的闸**,谁也替不了谁,故令牌那套一个字没删:

- **CAS 治「写覆盖」**:同进程 / 传播已收敛的并发,后写的拿旧版本号被挡下并**重判额度**;
- **CAS 治不了「读陈旧」**:跨渲染进程时两边都读到写入前的版本号,各自 CAS 都过 ——
  那一格仍然只能靠「写后等传播收敛 + 回读验令牌」分胜负(原注释里 12 轮 12 中的实测结论)。

### 🔴 踩坑留痕:实景判红绿之前,先证明「页面跑的是当前源码」

中途一度量到「被拒之后 UI 不刷新」,并按此写了一份缺陷结论。复核发现是**假象**:那一版页面
实例是跨着我改源码的过程一直开着的,dev server 给它的是**改动前的模块**。把源码 `cp` 还原到
与提交完全一致(sha256 逐字节校验)、强制整页 reload 之后,同样的步骤连跑两次都正确
(`conflict:true` + refs 同步 + 余额不动)。

教训与 `verify 绿 ≠ 渲染 OK`、`dev server 身份哨兵` 同族,补一条:**`location.reload()` 强制整页
重载 + 用页面上可观测的标识确认跑的是当前源码,再判实景红绿**;否则会把「页面在跑旧代码」
误判成「新代码有缺陷」,平白造出一条不存在的 bug。
