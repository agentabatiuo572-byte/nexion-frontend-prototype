## 1. 证伪(先证起点,再证结果)

主人给的现象是回源读码得出的,未运行时复现。**先跑复现再动手**,结论分两半:

### 核心判断成立(运行时证明)

注入一次落盘失败 → `applyWithdrawalDebit` 返回 false → 等真实的 5s 对账跑 ≥2 拍 → 余额 **4950 → 4950**,
幂等键 `wd-debit:` 内存与磁盘均未置位。

🔴 这条结论之所以站得住,靠的是同轮的**活性探针**:先抹掉同一张单的账单分录,
看 `reconcileBills` 的 ⓪ 格有没有把它补回来。⓪ 补回来了(证明对账确实执行到了那个函数),
而资金腿纹丝不动 —— 「余额没补」才排除了「循环压根没跑」这个平凡解释。
没有这个探针,那一格无论红绿都不说明任何事。

### 主人给的触发条件需要一处校正(缺陷不变,入口要多守一个)

「storage 写失败」这条入口**在生产档 remote 下不可达**:
`persistAccountSnapshot()` 第一行 `if (remoteApiEnabled) return true`(app.ts),
远端档恒真,`if (!persistAccountSnapshot())` 那条回滚分支根本进不去。

生产档真正可达的入口是**余额闸判假**(`authoritativeBalance < amount`)——
而 app.ts 余额闸那段注释**自己就写着**「而扣款**没有自愈** = 余额永久虚高」。
也就是说这一格当时被看见过,只是只绕开了一个具体触发(别写 `min()`),没有补自愈本身。

→ 两个入口都进了 runtime 门(A 落盘失败 / B 余额闸判假)。

## 2. 修法

`App.vue` 的 `reconcileBills()` 新增 ⓪b 格,与 ⓪ 是同一笔事实的两个面(⓪ 补账上那一行,⓪b 补余额里那个数):

```
for (const wd of app.withdrawals) {
  try {
    if (app.withdrawalDebitApplied(wd.id)) continue;
    app.applyWithdrawalDebit(wd);
  } catch { /* 一条脏单不拖垮整个对账循环 */ }
}
```

三个设计点(都会被门钉住):

| 决定 | 为什么 |
|---|---|
| 粗筛走内存判据,不每拍直接调扣款函数 | 后者在幂等命中时会 `adoptAccountSnapshot` 整体覆写状态,5s×每单 = 12 次/分钟全量覆写,正是 `refundWithdrawalDebit` 头注明确绕开的坑。判假只意味着「值得再问一次」,权威判定仍在函数内部读盘 |
| **不排除失败终态**,靠顺序闭合 | 本格排在 ② 退款腿之前,失败单补扣 −N 后退款腿当拍就退回 +N,净 0、不留跨拍中间态。排除失败终态就要在 App.vue 抄第五份终态字面量清单(全仓已有 4 份) |
| `try` 连粗筛一起包 | 只包扣款调用的话,粗筛自身抛异常会冲出循环打停 ①②③ —— 与注释承诺的爆炸半径不符 |

配套:`app.ts` 把幂等键拼法收成单源 `withdrawalDebitKey()`(此前 2 处手拼,本次新增第 3 个消费点)。

### 为什么不会翻出历史存量单批量重扣

`createSeedSnapshot` 与 `createServerEmptySnapshot` 都是 `withdrawals: []` + `appliedRewardKeys: {}` ——
单据与幂等键出自同一份快照、同生共死;remote 档 `bindAccount` 还会显式清空 `withdrawals`。
所以补扣只作用于本会话可见的单。

## 3. 门(两道,互补不是冗余)

| 门 | 守什么 | 守不到什么 |
|---|---|---|
| `selfcheck-fastlane.mjs` 接线门② | 补扣调用在、粗筛判据没写反、**排在退款腿之前** | 「它真的把钱补上了」 |
| `withdraw-debit-selfheal-runtime.mjs`(13 格) | 行为级:注入两种失败 → 等真对账 → 余额那个数真的变了 | **先后顺序**(13s 内跑 ≥2 拍会自己收敛) |

| 变异 | 静态门 | runtime 门 |
|---|---|---|
| M1 整格删除 | 🔴 红 | 🔴 红 |

M3 就是「两道门互补」的实证,已写进两道门各自的能力上界交底段。

## 4. 连带收口(修复让别处变成假话)

- `withdrawDebitFailed` 三语文案:原文「重开也不会自动更正」在自愈上线后成了假话,改「稍后会自动更正」。
  **en / zh / vi 三面都改** —— i18n 是三语不是双语,漏 vi 就是漏一面。
- `app.ts` 余额闸那段注释里「扣款没有自愈」已失效,原地交底,并补一句
  「自愈补的是本该成功却没落地的扣款,不是余额真不够」——防下一个人据此放宽闸。
- `verify.sh`:自愈门一度被塞在 `withdraw_bill_runtime_gate` 函数体内,拆成独立函数 + 独立调用行
  (否则删掉账单行那道门会**静默带走**本门)。

## 6. 本轮我自己踩的两个坑(判据抓回来的)

1. **runtime 门首跑 13 格红 5 格,差点归咎实现**:实为门脚本 `page.evaluate` 漏传金额常量,
   四张单 `amount` 全 `undefined`,扣款走的是**脏数据分支**而非被测分支 —— 而「注入生效」那三格**照样 PASS**。
   已加一格夹具自证(断言四张单金额等于构造值)。**起点断言只断言「返回 false」是不够的,
   要断言「是因为我注入的那个原因才 false」。**
2. **对比两次 verify 时先 grep 后剥 ANSI 颜色码,得到空集**,差点写成「没有新红门」。
   0 命中 = 判据失效,不是通过。修正顺序后才拿到真结论。

## 7. 已知边界(不在本卡范围)

- sandbox 档下 `reconcileBills` 首行即 return,本格不可达 —— 那条轨的钱包由服务端持有,一致。
- 余额真的不够时补扣仍会持续判假(每拍重试,纯读无副作用),直到余额回升。这是设计:
  自愈补的是「本该成功却没落地」,不是凭空造钱。
