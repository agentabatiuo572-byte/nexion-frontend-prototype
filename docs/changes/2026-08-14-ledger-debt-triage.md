# 86 条台账欠账逐条分类 —— 「PRD 欠 86 条」这个数是错的

主人 2026-08-14 交办「补 PRD 那 86 条」。逐条核完的结论是:**那 86 条根本不是一回事**,
混成一个数会得出「PRD 欠 86 条」这种错误结论,而真缺口是**个位数**。

---

## 三分类

| 类 | 条数 | 含义 | 该谁修 |
|---|---|---|---|
| **TBD-GAP** | **1** | 功能本身 PRD 没写 —— 真产品缺口 | 补 PRD 章节 |
| **TBD-NAME** | **71** | 功能 PRD 写了,只是没点名这个端点 | 台账的活,**不是 PRD 的活** |
| **NOT-PRD** | **14** | 基建 / 非本工程 / 沙箱 / 后台域 / 已退役 / 死路径 | 不该进前端产品 PRD |

分类结果写进台账每条的理由前缀,门的 PASS 行**分三个数报**,不再报一个笼统的 TBD 总数。
这样「欠账」这个词从此指向可执行的东西。

## 分类不是橡皮图章:抽查 3 条,错了 1 条

我按域批量分类后抽查了**最可能被分错的 3 条**,结果 2 对 1 错 —— 所以下面这句必须写清楚:

🔴 **TBD-NAME 那 71 条是按域推定的,不是逐条验证过的。**
抽查错误率 1/3 意味着里面**大概率还藏着真缺口**。要把它们变成可信结论,需要一轮
逐条「功能是否真在 PRD 里描述过」的审计,那是独立一张卡的工作量,本轮没做。
**别把 71 读成「这 71 条已确认没问题」。**

### 三条抽查的结果(留作判据样本)

| 抽查 | 初判 | 核实结果 |
|---|---|---|
| `/api/payment-methods` | TBD-NAME | ✅ 对。绑卡功能仍在(FEAT-TRIAL02 只是把它与试用解耦,没删),PRD §9.10 覆盖 |
| `/api/notifications/:param/actions` | TBD-NAME | ✅ 对。§11.2 写了通知的 CTA / 滑动 / 跳转;客户端方法叫 `recordAction`(我第一次按 `.actions(` 搜没搜到,**是我搜索模式错了**) |
| `/api/exchange/:param/cancel` | TBD-NAME → 一度改判 TBD-GAP | ❌ **两次都错**。见下 |

### 那条错得最有价值的:撤销兑换

- 第一判 TBD-NAME(功能应该被 §9.4.3 覆盖)→ 查 PRD,**0 处描述过「撤销」** → 改判 TBD-GAP(真缺口)
- 再回源查客户端 → `cancelRemoteOrder()` **定义了但零调用**,模板无绑定 → **用户根本点不到**
- 最终判 NOT-PRD(死路径),另立卡 `2026-08-14-card-dead-exchange-cancel.md`

**教训**:判「这是不是产品缺口」必须回源到**用户能不能真的做到**,不能只比对 PRD 文本。
「PRD 没写」+「代码里有」≠ 缺口 —— 也可能是死代码。两次判错都是因为少走了最后一步。

## 另一个盲区:台账门看不见「引用存在但不可达」

撤销兑换那条,接口地址**确实**在代码里被引用了,所以台账门判它有据、不报红。
门问的是「这个地址有没有被引用」,答不了「这条引用链最终有没有人走」。

**静态引用存在 ≠ 可达。** 要抓这类,需要的是另一种判据(从用户入口反向可达性分析),
不是给现有的门加规则。本轮不做,记在这里。
