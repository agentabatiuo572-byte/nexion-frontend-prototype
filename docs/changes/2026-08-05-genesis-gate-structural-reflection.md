## 二、四问(条款要求逐个回答)

### ① 根本路线选错没?

**没有。** 「购买可用性只在一处派生」这条不变量是对的,4/6 个消费者按它写、且写对了。错的不是路线,是**执行这条路线的机器门**。

### ② 是不是结构导致同型必然复发?

**是。** 而且是同一条结构缺陷,在三个地方各长了一个形态:

> **门的判据是「手写的枚举」,而它要守的是「开放集合」。**

- ④a/④b 手写「哪些字面形态算在外部做决策」→ 独立验收实测 **12 种本仓最惯用的写法全部放行**(解构改名 / 中间变量 / switch / `==` / `includes()` / 先赋值再判……)。这不是刁钻构造,是日常写法。
- ⑥ 手写「5 个紧迫感 i18n 键路径」→ Nova 用了第 6 个键,门**根本看不见它**。
- 消费者侧手写「阻断 → 文案」的映射,在 6 处各写一遍 → 4 处对、2 处错。

三者共同的根因**只有一条**:**判据是手写的、要守的面是开放的**。手写枚举永远追不上开放集合,所以同型必然复发 —— 不是「这次没想周全」,是**结构上不可能想周全**。

### ③ 族的共同根因 → 一条不变量/一道机器门根治(禁止逐个打补丁)

族里三个形态,根治法**不是把判据写得更全**(那是继续走 v1→v2 的老路,第三次还会死),而是**换方向:把开放集合改造成闭集合**。

| 形态 | ❌ 补丁式(禁止) | ✅ 结构式 |
|---|---|---|
| 外部重算决策 | 再补 12 种正则 | **收窄导出面**:store 不再对外暴露 `marketStatus` / `loaded` / `halted` 原料,只导出派生结果。原料拿不到 → E1-E8 十二种绕法**写都写不出来**。门退化成「原料字段名只许在 owner 出现」,而字段名定义在**唯一一处**,是闭集合。 |
| 文案逐档映射漏做 | 逐处补映射 | **一个 block→文案的函数**,消费者只能调它。没有第二个地方能写错。门:`genesis.marketClosed.*` 键只许在该函数里产生。 |
| 新消费者不接闸 | 往白名单加第 6 个键 | **判据反过来从 i18n 文件推导**:凡文案语义含稀缺/紧迫的键(三语全扫),其产出点必须引用闸。清单来自磁盘上真实存在的数据,不是手写的 5 条。 |

三条修法的共同点:**判据的来源从「我写的清单」换成「磁盘上已经存在的、唯一的那份数据」**。这正是 memory 里已有的 `feedback_batch_rewrite_ground_truth`(找 ground truth 别手写清单)与 `feedback_single_source_must_gate_its_consumers`(消费面是开放集合)—— **两条我已经记下来的教训,这次一条都没用上**。

### ④ 能机器测的焊机器门

三条全部可机器测,且都比现在的判据**更简单**(闭集合的判据总比开放集合短):

1. `genesis-config.ts` 的导出面不含原料字段名 —— grep 一个符号,闭集合。
2. `marketClosed` 键只在一个函数里被产出 —— 产出点计数 = 1。
3. 紧迫感键清单**由脚本从 i18n 文件生成**,不硬编码;其产出文件必须引用闸。

🔴 三道门都必须**先红测再算数**,且按已有铁律「按合取项逐个隔离」——因为这次实测还发现:④b 的红测写成 `A || B`,`marketStatus` 那支恒真,导致 `loaded` 那支**整条坏掉也照绿**。同一族(哨兵假绿)第 N 次。

## 三、结论(条款要求二选一)

**确认存在结构性问题 → 先改结构,再继续 R。**

在导出面收窄 + 文案映射收口 + 紧迫感清单改为推导之前,**不允许再往门里加正则**。往门里加正则就是在坏地基上刷漆,v1→v2 已经证明过一次。

## 三·补 · 修法可行性实测(我提的修法本身也是待核断言)

上面的方向如果落不了地就是空话,所以**动手前先量了真实消费面**(2026-08-05 实测,排除 owner 自身与 i18n 文件):

| 原料字段 | 消费文件数 | 分布 | 收窄可行性 |
|---|---|---|---|
| `marketStatus` | **2** | `store/genesis.ts`(3)· `composables/use-genesis-sale-gate.ts`(3) | ✅ **最容易**。两个都是合法的二层 owner,收进去即可,页面侧本来就没人碰 |
| `closedNoticeKey` | **5** | 上述 composable + `genesis.vue` / `marketplace.vue` / `genesis-showcase-card.vue` / `purchase-sheet.vue` 各 2 处 | ✅ 4 个页面各自**独立映射文案** —— 正是未修#1 的族。抽**一个 `block → 文案` 函数**后,消费面 **5 → 1** |
| `halted` | **6** | 上述二者 + 4 个页面/组件 | ✅ 页面碰它是为了**给纯函数拼装入参**。让 store 直接暴露算好的 `block`(computed),页面就不必拼装,消费面 **6 → 0** |

**实测带来的关键修正 —— 根因比我反思时写的更靠前一层**:

> owner 导出的是一个**要求调用方自己拼装入参**的纯函数(`genesisPurchaseBlock(input)`)。
> **正因为要拼装,每个调用方都必须合法地摸原料** —— 于是「谁摸了原料」这个判据从一开始就分不出好坏,
> 门只能退而去猜「摸了之后有没有自己下结论」,而那是开放集合。

所以真正的第一性修法不是「禁止摸原料」,是 **让调用方根本不需要摸**:

- store 暴露 `block`(已算好的 computed)与 `blockText`(经唯一映射函数),
- 纯函数 `genesisPurchaseBlock` 保留但降为**内部实现**,
- 于是页面侧对三个原料字段的引用应当**归零** —— 而「某符号在某目录下出现次数 = 0」是**闭集合判据**,一行 grep 说了算,不需要 12 条正则。

📌 **门的判据随之改写**(从开放集合换成闭集合):
`marketStatus|closedNoticeKey|halted` 在 `src/pages/` 与 `src/components/` 下出现次数必须 = **0**;
owner 与两个二层 owner 之外的任何引用即红。红测:往任一页面塞一处引用 → 必红。

## 三·补二 · 回源看真实的行之后,修法进一步缩小(2026-08-05)

上一节只数了**次数**没看**内容**,结论偏大。逐行回源后事实是:

`use-genesis-sale-gate.ts` **已经**是单一消费入口,已导出 `block` / `showUrgency` / `marketClosed` 等派生值。
页面并没有自己重算判定 —— 它们重复的是**另一件事:把 block 翻译成文案**。

**真实分布(6 处)**:

| 处 | 现状 |
|---|---|
| `genesis.vue:264-274` · `marketplace.vue:163-170` · `purchase-sheet.vue:135-141` · `genesis-showcase-card.vue:120-132` | 各写**一份相同的 switch**,都在做 `t.genesis.marketClosed[closedNoticeKey as "default"] ?? 兜底` |
| `quick-action-row.vue:62` · `holder.vue:233-237` | **连 switch 都没写**,直接写死 `.default` ← 未修#1 的用户可见缺陷 |

即:**判定没散,散的是「判定 → 文案」这一步**。而 `closedNoticeKey` 之所以要导出给页面,唯一原因就是让它们各自做这一步。

**因此修法收缩为一件事**(比原计划小得多,且是纯删除性收敛):

> 在 composable 里加 `blockText`(**一个** switch,含 `closedNoticeKey` 变体查找与兜底),
> 6 处全部改用它;`closedNoticeKey` **不再导出**。

连带效果:
- 4 份重复 switch **删掉**(含重复 4 次的 `as "default"` 类型断言,本身是坏味道);
- 2 处写死的自动拿到正确文案 —— **未修#1 不需要单独修**;
- `closedNoticeKey` 在 `pages/` `components/` 出现次数 → **0**,判据变成一行 grep 的**闭集合**;
- 门里 ④a/④b 那堆猜形态的正则可以**整段删除**,不是再加。

### 🔴 合并前必读:4 份 switch **并非全等**,盲目合并会静默改行为

逐份对比后(2026-08-05 实测),它们分成**两半**:

| 档 | 4 处是否一致 | 结论 |
|---|---|---|
| `configUnavailable` / `marketClosed` / `halted` | ✅ **四处逐字相同**(含 `[noticeKey] ?? default` 兜底) | **这三档才是可抽取的公共部分** |
| `soldOut` | ❌ 创世页 → `genesis.ctaSoldOut`;商城卡 → `store.genesisCardCtaMarket`(**去二级市场**) | 各面 CTA 词汇本就不同,**不是重复** |
| `preSale` | 创世页 / 商城卡 → `comingSoon`;另两处落进 `default:` | 同上 |
| `null`(可购买) | 创世页 → 资格门 → `ctaReserve`;商城卡 → `cardCta` | 同上 |

**若把 5 档一起合并,商城卡的售罄文案会从「去二级市场」被悄悄改成「已售罄」** —— 一次没人要求、也没人会立刻发现的行为变更。这正是重构最典型的伤人方式。

**因此 `blockText` 的契约收窄为**:

> 只负责**三档阻断说明**(`configUnavailable` / `marketClosed` / `halted`),
> 其余档一律返回 `null`,**逼调用方显式处理自己的 CTA 文案**。

顺带修掉一处既有脆弱:`purchase-sheet` 与 `marketplace` 现在靠 `default:` 兜住「可购买」态
—— 即 block 为 `null` 时它们也会算出一句「市场暂未开放」,只因外层另有 `sheetBlocked` /
`marketClosed` 闸挡着才没露出来。**返回 `null` 后,这种「靠外层碰巧挡住」的写法会直接暴露成类型错误。**

### 🔴 暴露出的盲维(比这 4 条本身更重要)

`purchase` / `acquireSecondary` 都调了闸,`listNode` **一次没调**;Nova 气泡同样一次没调。
我的门查的是「**引用了闸的地方,用得对不对**」——它**永远看不见「本该引用却完全没引用」的地方**,
因为那些地方连一个可匹配的符号都不出现。

这正是 `done-review` 元模式 #1 **维度盲区**:查了「存在的对不对」,漏了「**该有的在不在**」。
两者正交,一道门只能覆盖一维。

**修法(仍走闭集合)**:「会改变持有状态的 genesis action」是一个**闭集合**。
判据:**这些 action 每一个都必须调用某个 block 判定**;新增一个不调的,门必红。
台账写在门脚本里(不写在被查文件里),0 命中即判据失效。

🔴 **但「闭集合」锚在哪里,是这道门成败的关键 —— 我第一次就锚错了**:

我先写了个扫描,**按「函数体里有没有写状态关键词」**去筛。结果它**静默漏掉了 `listNode` 本身**
(正是 P0-4 的主角)和 `setNexListed` —— 筛选正则与实际写法大小写不匹配之类的原因,
而扫描**不会报错,只是少列两行**。若照它建门,P0-4 这类缺陷**永远不会被门看见**。

**正确的锚点是 store 自己的导出块**:`store/genesis.ts` 末尾那个 `return { … }`
把 24 个成员**在唯一一处**显式列了出来。它是磁盘上已经存在的、真正封闭的清单,
不依赖我发明任何模式。

> **判据锚点必须是「代码里已经存在的显式清单」,不是「我写的模式」。**
> 模式会漏(而且静默),显式清单不会 —— 新增成员必须写进那一处,门就一定看得见。

这与 [[feedback-batch-rewrite-ground-truth]](找 ground truth 别手写清单)是同一条道理,
只是这次它出现在**门的判据**上,而不是批量改写上。**今天这是我第三次自造判据有洞**
(前两次:`\b` 变退格符恒绿;只做样本量不做阳性对照)。

# 五、包 H 收口台账 —— 未修项与**被否决**的修法(2026-08-05,主人拍板走推荐 A)

## 5.1 记账不修:周任务在闸变化时重派,作废「已完成未领取」

**现象**:用户点了「买创世」CTA → 运营关市场 → `dispatchTier1` 换成别的任务 →
`completed` 变 false、领取键消失。反向(closed→open)同样作废 `stake_fallback` 的完成。

**为什么不修**(独立证伪 agent 逐条给的依据,已回源坐实):

| 提出的修法 | 它会造成什么 |
|---|---|
| 钉住已完成的任务不再重派 | `markTier1Complete` 是**点 CTA 就触发**的(`weekly-quest-hero.vue` onCta,注释自陈),钉住 = 点一下、市场随即关闭,没买创世照样领 2500 NEX + 徽章 |
| 同上 | 钉住那一支绕开 `genesisPurchasable` 判据,创世闸对它彻底失效 |
| 同上 | `tier1Completed` 是从 storage 裸 cast 的字符串,脏值 → `TIER1_QUESTS[脏值]` 为 undefined → 整周不出任务卡,且周冠军奖永久不可领 |

**结论**:现在这版「闸一关任务就换掉」**方向是对的**——它的错误方向是「少发」而不是「多发」。
真正的修法是在服务端按**行为归因**判完成(本文件所在工程已是 backend-replaceable 的形状),
而主人已明令本阶段不写后端接口。

**残留风险(接受)**:真买了创世的用户,若运营恰在其点 CTA 与领取之间关闭市场,会丢一次
2500 NEX。发生条件苛刻,且运营可手工补发。

**什么时候该回来做**:后台真接线、`markTier1Complete` 能由服务端行为归因驱动时。
届时连带做掉下面 5.2。

## 5.2 同型未修:tier2 也是实时重洗(A5)

`dispatchTier2` 的 eligible 池吃**实时**余额 / NEX / 是否有硬件,余额跨 $100/$200 档
或买了硬件就重洗 → 已完成未领的 tier2 行同样会消失。与 5.1 同根因、同结论,同一批修。

## 5.3 等接线自然消失:存储探针在默认态仍每次写盘

`hydrate()` 已改成**先读、读到合法配置就不写探针**。但全仓 `useGenesisConfig().update()`
/ `reset()` **零调用方** —— app 自己从不持久化创世配置,读回来永远是空,于是默认态下
探针照跑。后台真接线后配置会落盘,这条自然消失,**不必为它现在加任何机制**。

## 5.4 🔴 被否决的修法(下轮再被提出时,先看这里)

| 提案 | 否决理由 |
|---|---|
| 探针结果加时间窗缓存 | 缓存期内源真坏掉会把 fail-closed 翻成 **fail-open**(已关的市场重新开门且可下单);而 purchase / listNode / acquireSecondary 三处动钱前的 `refresh()` 要的正是**当下**的源 |
| 探针键加随机后缀 | 固定键自覆盖;随机键在 remove 失败时**每次冷启动泄漏一条**(小程序端同步存储有 10MB 上限)。而它要防的键碰撞并不存在——全仓只有这一处生产者 |
| 探针 token 改成常量 | 唯一 token 证明的是「**这一次**写落地了」;常量会在「remove 失败 + set 失败」组合下读回上一轮残留值而误报 OK |
| 钉住已完成任务 | 见 5.1 |

## 5.5 本轮真正学到的一条(已进 memory)

**手写清单漏掉的不是「我新加的」,而是「本来就在的」。**

我给 verify 补缺兄弟仓跳过时,照着「我加了哪个齿」写清单。红测一跑,链其实断在**更早的
第 15 齿**——那是早就存在、早就读兄弟仓的齿,后面 20 个齿一次都没跑过。
而且旧清单还把 `real recharge-channel parity` 归错了仓。

修法不是把清单补全(它还会漂),是换机制:**检测而非预测**——照常跑,齿真的非零退出时
再看输出是不是缺仓的特征错误。副产品:找回 2 个被旧清单**误跳**的齿(27/34 → 30/35)。

> 注意反例:一开始想的是「扫脚本源码里提到哪个仓 → 派生清单」。实测提到 nexion-backend
> 的脚本有 30+ 个而真炸的只有 5 个 —— **按提及派生会过度跳过,比漏跳更糟**(静默少跑
> 20 多个齿)。开放集合的问题不是都能靠「扫一遍」解决的。
