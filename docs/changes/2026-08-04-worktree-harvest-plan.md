## 四、完全版 A 的实施要求(来自方案证伪,不可省)

**主人已选完全版**:资金字段**真正只存在一个地方**,需先把现有账户快照拆成「高频(收益/设备)」与「低频(资金/提现/账单)」两张表,再把账单并入低频表。

🔴 **证伪给出的三个墨菲点(验法是"数出来"不是"看功能对不对")**:
1. **每秒心跳热路径**:账户快照落盘挂在 `App.vue` 的 1 秒 `setInterval` → `tick()` → `settle()` → 无条件落盘。
   **验法**:改完后打开一个有活跃设备的账号,**静置 60 秒不操作**,数 `nexgrid-account-cloud-v1` 的写盘次数与 payload 大小。
   完全版必须做到:**账单不在每秒重写的那张表里**。
2. **合并函数逐字段枚举**:`mergeAccountSnapshots` 不会自动合并未列出的字段 —— 新字段若不显式加合并分支,会退化成整表 last-write-wins(**"合并把账单合丢"会真实发生且无哨兵报警**)。
   **验法**:双标签页红测,A、B 各提交一笔,合并后账单**必须是两条不是一条**;并同步补 `spec4-account-cloud-merge-check.mjs` 用例。
3. **迁移漏掉其它账号**:账户表是**多账号共享一个 key**,只迁当前登录账号会让其余缓存账号长期双份不同步。
   **验法**:迁移前在同一浏览器造两个账号的数据,迁移后**分别登录**验证账单都在。
   建议照抄既有 `upgradeLegacyWithdrawals` 的「读时升级、不做批量迁移脚本」范式(幂等、无新增失败面)。

🔴 **已被证伪、不许走的路**:「账单成为唯一真相、余额由账单推导」——历史事故:按账单累加算余额与真实余额**差 400 倍**,因为账单只是**部分流水**(心跳累积的收益从不进账单)。

🔴 **并发方案不许叠加**:仓内现有三套(账户快照三路增量合并 / 质押的版本号并发 / 账单的裸读写)。合并后**二选一**,不要 CAS 通过后再跑三路合并(两套失败语义会搅在一起)。证伪建议留在三路合并体系(改动面更小)。
