## 三、逐格裁决:失败结局判据(钱路径)

用途:一笔提现请求失败后,幂等键**留着原样重放**还是**作废重铸**。判错一个方向 = 服务端出第二笔。

| 错误 | 主线原判 | 并入侧原判 | 裁决 | 理由 |
|---|---|---|---|---|
| http 409 | 确定拒绝 | 服务端已有该键记录 | **并入侧** | 409 字面意思就是「这把键已有记录」;判成拒绝 → 换新键重发 → 真出第二笔 |
| http 429 | 确定拒绝 | 歧义 | **并入侧(通用)+ 主线(具体)** | 通用 429 归歧义(网关限流时上游可能已转发);**日限拒单**这个已知的具体 429 由页面分诊第一档认掉,比通用判定更准。靠**顺序**共存,不是二选一 |
| configuration | 确定(请求没发出) | 歧义 | **并入侧** | 主线的理由**在今天成立**,但它依赖「configuration 全部抛在请求发出之前」这个**没有任何门看得住的前提**。日后谁在响应处理里抛一个,「确定没建单」就静默变成重复出账。保守代价 = mock 模式多留一把没用过的键;判错代价 = 真出第二笔。不对称,取保守 |
| 408 / 425 | 408 歧义 / 425 未覆盖 | 都歧义 | 并入侧 | 语义都是「我可能已经收到了」 |
| network / protocol / 5xx | 歧义 | 歧义 | 一致 | — |
| business / auth | 确定 | 确定 | 一致 | 服务端明确应答并拒绝 |

⚠️ 因此改了 `selfcheck-withdraw-failpaths.mjs` 的两条断言。**改测试而不是改实现**,
理由写在断言旁边,不静默翻转 —— 两侧各自钉死了相反结论时,裁决必须留痕。

### P0-1 · 日限那档抢在「定局判定」之前退役幂等键,而它的判据是**服务端可控文本**

- 位置:`src/pages/me/wallet-withdraw.vue:1289-1293`(第①档)· `:565-570`(判据定义)
- 核实:`isDailyLimitRejection` 只做 `err.message.toUpperCase()` 的子串匹配
  (`DAILY_LIMIT` / `DAILY_COUNT` / `WITHDRAW_LIMIT_EXCEEDED`),**不看 kind、不看 status**;
  而 api-client 对任何非 2xx 都把服务端 envelope 的 message 原样透传。
  行号确认:①1289 → ②1295(409)→ ③1301(定局),第①档必先执行,命中即 `forgetWithdrawAttempt`。
- **怎么来的**:我做四档并集时,把这一档从旧机制的 `clearSubmitIntent()`(清一个没人读的 ref,无害)
  直译成了新机制的 `forgetWithdrawAttempt()`(**退役钥匙 = 下次铸新键**)。同一个动作名,
  在新旧两套架构下的语义完全不同 —— 这正是「并集」最容易出错的地方。
- **后果**:首提建单成功但网关超时 → 键留盘(正确)→ 用户重发 → 同键重放 →
  服务端若把日限校验排在幂等去重之前,返回 429 + `DAILY_LIMIT` 文本 → **命中第①档,键被退役** →
  用户按页面倒计时提示次日再提 → 铸新键 → **服务端出第二笔**。客户端全程看不到第一笔。
- 🔴 附带证据:该函数自己的头注写着「只用于换一句更准的话……认错也不会放行或拦截任何东西」。
  合并后它门控 `forgetWithdrawAttempt`,**这句注释已经是假的**,而假的方向正好是钱。
- **计划修法**:把「换哪句话」与「键的去留」**拆成两个决定**。日限只负责话术;
  键的去留一律由 `isSettledRejection` 决定。即
  `if (isDailyLimitRejection(err)) { if (isSettledRejection(err)) forgetWithdrawAttempt(...); toast(...); return; }`
  并把头注改回与代码一致。
- **门**:现有两道门都不守这一格 —— freeze 门只检查 catch 里**出现过**两个函数名,
  不检查第①档动不动键;failpaths 只测判定函数,不测页面接线。需补一道。
