# 包 z5 审计溢出项 —— 建议独立成卡(2026-08-11)

包 z5(提现建单成功后本地扣款 + 失败退款配对)走 nexion-audit 时,6 个独立审计 agent
+ 1 个对抗证伪 agent 报出的、**不属于本包范围**的发现。本包已修的属于本包的缺陷不在此列。

分级依据:对抗证伪 agent 对「本次引入 vs 既有家族」逐条做了归属判定,下表采用它的结论
(它对包 z5 自己的两条主张也做了证伪,不是一味确认)。

---

## 建议排期(main 的推荐,供主人拍板)

| # | 项 | 我的推荐 | 为什么 | 不做会怎样 |
|---|---|---|---|---|
| B | 扣款无自愈 | **先做**(建议紧接 z5) | 它是 z5 修复的**残余漏面**:低概率但后果与原缺陷同形(账单挂着 −$N、余额没少);且修法已有明确边界(只补带标记的新单),风险可控 | 落盘失败/换号那几种情况下,z5 修的缺陷原样复现,且无人发现 |
| E | 缺 `GET /api/withdrawals` | **先做**(与 B 同批) | **多条发现的共同根**:补上它,C(歧义单看不见)、`frozen` 单状态永停、到账靠本地时钟猜,半数条目一次收口 | 客户端永远只能靠建单那一次回执,任何「事后才知道」的结局都补不回来 |
| A | 资金原语家族无跨页事务 | **单独立卡,不要塞进业务包** | 是家族级架构改动(CAS 迁移),影响购买/质押/兑换/复投全部路径;`account-cloud` 头注证明它是**已知取舍**而非疏漏 | 维持现状:并发超卖被静默夹掉。真后端单事务上线后自然消失 |
| F | 质押 `refunded`/`slashed` 零消费者 | **成卡,优先级同 B** | 与 z5 完全同型(本地扣了钱 + 服务端可给终态 + 客户端没有对应的腿),z5 只修了提现那一份 | 质押被服务端退款时用户拿不回钱,也看不到这个状态 |
| G | 扣没扣/退没退零可见面 | 并入 B 一起做 | 加一行文案的成本,却是客服唯一能查的凭据 | 出问题时用户和客服都只能猜 |
| C | 歧义幂等键离页即失 | 等 E 落地后再做 | 没有单据查询端点就补不回来,单独做只能治一半 | 极低概率下服务端出第二笔而客户端看不见 |
| D | NEX 抵扣费账实背离 | 维持现状(主人已成卡) | 需要服务端先定退还契约,客户端单方面动只会造出「只烧不退」 | 账单上 −N NEX 一直没有对手方 |
| H | 门的模式覆盖边界 | **成卡,但不急** | z5 已对提现这一族焊了静态判据兜住;全仓性评估值得做,但没有正在流血的伤口 | 其它 `remoteApiEnabled` 分支仍对全部 runtime 门隐身 |

**一句话**:B + E + F + G 建议排成下一批(它们互相咬合、且都指向「事后才知道的结局」这一类);
A 和 H 是架构级评估,单独立卡;C 依赖 E;D 等服务端。

## A. 资金原语家族:mock 持久层没有跨标签页事务

**现象**:所有本地资金原语都是「读内存 → 算 → 写绝对值 → 交给 additive merge」。
两个标签页各扣一笔各自合法的钱,合并层把两笔 delta 都累加成负数,再被
`clampAccountFundInvariants`(`src/store/account-cloud.ts:379`)静默夹到 0 ——
**超卖被吞掉,而函数照样返回 true**。实测:余额 100,两页各提/各花 60 → 盘上 0(真值 −20)。

**归属**:既有家族,**且是有意设计** —— `account-cloud.ts:374-378` 头注已明写
「多端并发扣款(各自本地合法)合并时两笔扣款都累加 → 扣穿为负…真后端单事务天然不会;
mock 层在写盘前统一收口」。`debitBalance` 与本包新增函数完全同形,购买 / 组合 / 质押 /
兑换 / 复投全部走它。

**为什么仍建议成卡**:头注只说了「不落负余额」,**没说它同时吞掉了差额并让调用方看不见**。
「返回 true = 钱真的按 amount 扣掉了」这个假设被全仓调用方普遍持有,而它在并发下不成立。

**候选修法**:`src/store/account-scoped-storage.ts` 已有 `writeAccountRowCas`(rev 比对),
把资金原语家族整体迁到 CAS;或至少让 clamp 生效时向调用方报假。**这是家族级改动,
不该挂在单个新函数上。**

---

## B. 扣款没有自愈,账单有 —— 两条腿的自愈能力不对称

**现象**:账单行丢了,`App.vue` 的 5s 对账会照单据补回来(⓪ 段);**扣款丢了就永久丢**。
四条触发:落盘失败、余额不足、提交期间换号、await 期间关页面。
后果:账本挂着 `−$N`、余额一分没少 —— 正是 z5 要修的那个原状态,只是概率低。

**归属**:本包新增扣款腿时一并带来的结构缺口(账单侧 z4 已有自愈)。

**🔴 修法警告(审计明确点名,别照抄账单那条路)**:**不可**无条件遍历 `app.withdrawals` 补扣 ——
2026-08-10 remote 对齐期建的存量单**全都没有** `wd-debit:` 键,一次性批量追扣会让用户
余额无解释地掉一大截。范围必须用「提交时落一个本地待扣款标记」钉死,只对带标记的单重试。

---

## C. 歧义结局的幂等键离页即失

**现象**:提交幂等键存活在提现页实例的 ref 里(`wallet-withdraw.vue` 的 submitIntent)。
「服务端已建单但响应丢失」时用户离开页面再回来,键归空 → 重试用新键 → 服务端可能真出第二笔,
而客户端只见到第二张单、只扣一次款。第一笔单客户端**永远看不见、永远不会被扣款**。

**归属**:既有(z5 之前就是这样),但 z5 让后果多了一层(那笔看不见的单也不会被扣款)。

**依赖**:与 E 同根 —— 没有单据查询端点就补不回来。

---

## D. NEX 抵扣费:账实背离

账单写 `−nexBurned` NEX 行,而客户端从不 `debitNex`(全仓零调用点),`nexBalance` 永远虚高;
失败提现退还已烧 NEX 也没有服务端契约(`App.vue` ②b 头注已登记)。
**主人已单独成卡**,此处仅登记它与 z5 的关系:z5 只处理 USDT 本金腿,NEX 腿一个字没动。

---

## E. 没有单据查询端点 `GET /api/withdrawals`

`src/api/withdrawal-api.ts` 只有 `policy` + `submit`。由此派生:单据状态永不刷新
(`frozen` 单钱已扣、状态永远停住)、丢单不可恢复、歧义单看不见、到账全靠客户端本地时钟猜
(`advanceWithdrawalArrival` 按本地时间把 pass 单推成 confirmed,从未与服务端核对)。
**多条发现的共同根,补上它可一次收口半数条目。**

---

## F. 质押的 `refunded` / `slashed` 终态零消费者(同型排查发现)

`src/store/staking.ts:61` 与 `src/api/staking-api.ts` 声明并解析这两个服务端终态,
而全仓**没有任何消费者**(既不入账、也不渲染)。开仓时 `stake-sheet.vue` 经 `postMoneyBill`
真扣了钱,服务端若判 `refunded`,客户端不会退回,用户也看不到这个状态。

**与 z5 同型**:「本地扣了钱 + 服务端可给终态 + 客户端没有对应的腿」。z5 修的是提现那一份。
(对照:订单侧的 refunded/chargeback 归并为「已取消 + 退款已排队」,是有意的人工流程,不算缺口。)

---

## G. 客服/用户侧:扣没扣、退没退,产品内零可见面

唯一痕迹是 localStorage 里的 `wd-debit:<单号>` / `wd-refund:<单号>` 两个布尔键,
无导出、无客服可读编号;扣款/退款失败也不入 `stuckFundsCases()` 待对账队列。
建议提现进度页加一行「本机余额已扣减 / 未扣减 + 单号」。

---

## H. 机器门的模式覆盖边界(已在代码注释登记,此处备查)

`verify.sh` [2.5] 强制 dev server 跑 **mock** 模式,而产品跑 **remote**,
且提现单**只在 remote 建得出来**(mock 下 `createMockModeApiClient` 让每个请求 reject)。
于是任何 `if (remoteApiEnabled) …` 分支对全部 runtime 门天然隐身 ——
z5 修的那条「退款腿在 remote 下恒 no-op」正是这么藏住的。
z5 已对两条腿各焊一条静态判据兜住这一面,但**这是全仓性的门覆盖边界**,值得单独评估。
